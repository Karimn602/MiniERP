# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**Lira POS** is an offline-first desktop Point of Sale and inventory management app for Lebanese retail. Built with Tauri 2 (Rust + Chromium shell), React 19, and SQLite. All data lives locally; no backend server. The "mini ERP" framing means it also covers purchasing, supplier ledgers, and accounting scaffolding.

## Commands

All commands run from `lira-pos/`:

```sh
npm run dev        # Start Vite dev server (port 1420) — frontend only, no Tauri shell
npm run tauri dev  # Full Tauri desktop app with hot-reload (needs Rust toolchain)
npm run build      # TypeScript check + Vite bundle
npm run tauri build # Full desktop build (produces installer)
```

Tests and checks (also from `lira-pos/`):

```sh
npm test             # vitest: unit + SQL/read-model integration
npm run test:types   # typecheck the test tree
npm run test:rust    # cargo test — the authority on posting and migrations
npm run check:rust   # cargo check
npm run verify       # all of the above, in order
```

`npm run verify` is the gate. There is no lint script; TypeScript strict mode
and the test suites are the safety net.

## Architecture

### Stack
- **Desktop shell**: Tauri 2 (Rust)
- **UI**: React 19, React Router 7, Tailwind CSS
- **State**: Zustand (two stores: `activeContext`, `lowStockBadge`)
- **Database**: SQLite via `@tauri-apps/plugin-sql` — single file, WAL mode, foreign keys ON

### Critical Design Decisions

**Money is always integers.** USD stored as cents, LBP stored as whole lira. Never use floats for money. Exchange rates and VAT rates are stored as integer basis points (e.g., 1100 = 11%).

**Unit cost is a rate, not an amount — it is stored in microcents.** Money (line totals, VAT, tender, COGS amounts, the supplier ledger) is cents. A *unit cost* is money per base unit, and when the purchasing UoM dwarfs the base UoM that rate is legitimately below a cent: flour at $2.50/kg stocked in grams is $0.0025/g. So every per-unit cost column has a microcent sibling (`1 cent = 1,000,000 microcents`) which is the accounting source of truth:

| cents (display mirror) | microcents (authoritative) |
|---|---|
| `products.avg_cost_*_vat_cents` | `products.avg_cost_*_vat_microcents` |
| `inventory_movements.unit_cost_*_vat_cents` | `inventory_movements.unit_cost_*_vat_microcents` |
| `purchase_items.unit_cost_*_vat_base_cents` | `purchase_items.unit_cost_*_vat_base_microcents` |
| `sale_items.unit_cogs_excl_vat_cents` | `sale_items.unit_cogs_excl_vat_microcents` |
| `sales_credit_memo_lines.unit_cogs_excl_vat_cents` | `sales_credit_memo_lines.unit_cogs_excl_vat_microcents` |

Rules: all cost arithmetic goes through `src-tauri/src/cost.rs` (or `src/lib/cost.ts`), never a hand-rolled multiply-and-divide. Rounding is half away from zero, in one helper. Cost becomes money exactly once, at `extended_cost_cents` — precise rate × base quantity, rounded once; never round the rate first. The `*_cents` columns are maintained by the posting commands as `round(rate)` for display and back-compatibility, and must never feed a calculation. The per-UoM invoice cost (`unit_cost_*_in_uom_cents`) stays in cents: it is what the supplier billed, exact to the cent.

**UoM conversions use rational fractions.** Each `product_uom` row has `conversion_num` / `conversion_den` to preserve precision when converting between units (e.g., kg → g).

**Transactions run in Rust, not JavaScript.** The eight `invoke` handlers in `posting.rs` (`post_purchase`, `post_sale`, `post_credit_memo`, `post_adjustment`, `post_supplier_payment`, `post_driver_remittance`, `open_shift`, `close_shift`) are the only place that mutates financial and inventory state. This avoids JS connection-pool race conditions. Frontend repos are read-only query helpers.

**Compound CATALOG writes run in Rust too, for the same reason.** `catalog.rs` holds four more handlers — `save_product`, `add_product_barcode`, `set_primary_product_barcode`, `remove_product_barcode` — because saving a product is a compound write (a `products` row, one or two `product_uoms` rows, sometimes a barcode, and on an update a clear-then-set of the default sale UoM) and tauri-plugin-sql gives no usable BEGIN/COMMIT across statements. The half-states are UNLOADABLE, not merely untidy: `productsRepo.enrich` refuses a product with no base UoM or no default sale UoM, and it refuses it while loading the LIST, so one product broken by a duplicate SKU takes the whole Products page down. Reporting and read queries stay in TypeScript — a read has nothing to be atomic about.

**The database decides the UoM conversion, not the payload.** `post_sale`, `post_purchase` and (since WP-07) `post_adjustment` all resolve the product's own active `product_uoms` row — looked up by `(product_id, store_id, uom_code, is_active)` — and derive `quantity_base` from *its* factor. That single resolved conversion drives the per-base cost, the persisted snapshots, the inventory movement, `quantity_on_hand`, the weighted average and the last-purchase rate. A payload that declares a different factor, base quantity or `product_uoms` row id is **refused**, not silently normalized: the buyer priced the goods against the conversion they believed in. Client-supplied `quantity_base` / `factor_*_snapshot` / `product_uom_id_snapshot` remain on the wire for compatibility and are cross-checks only.

An **inventory adjustment is a UoM quantity**, not a base-unit one: the Inventory screen has the manager pick a `product_uoms` row, type a whole number and a direction. `post_adjustment` was the last command to still believe the client's conversion — it moved stock by the payload's `quantity_base_signed` and stamped the movement with the payload's factor, unchecked — so a request could say "−1 each" and move 1,000 base units, leaving an audit trail that actively denied the discrepancy it created. Since WP-07 it resolves, derives and refuses exactly as its two siblings do, and the movement row carries the resolved factor so the stock delta and the cost metadata always describe one conversion. Adjustments are still valued *at* the current weighted average and never move it: a quantity correction is not a cost event.

**An inventory adjustment's negative-stock policy is a decision about the DOCUMENT.** Greaz forbids an adjustment that leaves stock below zero, and that rule is applied once per product to the document's NET base delta, not per line. Nothing is written until every line is resolved, so each line of the same product reads the same opening quantity — two lines of −6 against an opening 10 each saw 10, each computed a resulting 4, and each passed, committing −2 under a rule that forbids it. The Inventory screen appends a line per pick with no merge, so a manager counting one shelf twice reached this. The resolved deltas are aggregated by product with `checked_add` and judged once; each line still writes its own movement row, so the audit trail records what was entered and still sums to the validated net.

**One open shift per store, and the shift is checked when a sale posts.** The shift scope is the store — `getOpenShift(storeId)` queries `(store_id, status='open')`, `device_id` is never populated, and the cashier is recorded but not scoped on. `open_shift` decides uniqueness in a single `INSERT ... WHERE NOT EXISTS` statement, backed by the partial unique index `ux_shifts_one_open_per_store`; `close_shift` computes the cash reconciliation and writes it in the same transaction that marks the shift closed, and a closed shift is immutable (`trg_shifts_no_update_after_close`). **A new sale must name an open shift of its store** — `post_sale` refuses one that does not, inside its own transaction and before any receipt number or row is written. The check runs *after* the idempotency resolution, so retrying a sale that already posted still returns its original receipt, including a historical row whose `shift_id` is NULL. `sales.shift_id` stays nullable in the schema: the rule governs what may be written from now on, and history is not rewritten.

**Tender is validated, never trusted; change is cash.** A payment row's `amount_usd_cents_equivalent` is *derived*: a USD tender's is itself, an LBP tender's is its lira at the rate locked on the sale, and that locked rate is matched against the `exchange_rates` row (scoped by store) before anything is written. Non-cash tender may never exceed the amount due, so a card overpayment is refused rather than written as drawer change, and the row absorbing an overpayment is always a cash row (USD cash preferred, else LBP cash, in that row's own currency). Expected drawer cash is `opening float + cash in − change out − cash refunds out` per currency (the refund term since WP-06), counting only `cash_usd`/`cash_lbp` rows in every term.

**One authoritative unit price per purchase line.** A supplier invoice quotes ONE price per unit, and `vat_pricing_mode` on the line says which side of the excl/incl pair that is — the payload's value (the Purchases page's per-line Incl/Excl toggle), or the product's own `products.vat_pricing_mode` when the payload omits it. The counterpart is *derived* by `post_purchase` with the application's own VAT rounding (`posting.rs::add_vat` / `strip_vat`, mirroring `lib/vat.ts` in integer arithmetic), and a declared counterpart that disagrees is **refused**. Exclusive mode → `unit_cost_excl_vat_in_uom_cents` is authoritative; inclusive mode → `unit_cost_incl_vat_in_uom_cents` is. At 0 bps the two must be the same figure. Rounding to whole cents means `add_vat` and `strip_vat` are not exact inverses, so the mode is what fixes the direction rather than the backend guessing. Without this, a line could declare "$20.00 net, $999.00 gross" at 11% and stock inventory at a $20 cost basis while raising $999 of supplier debt.

**A purchase's payable is derived, and a supplier invoice posts once.** The AP liability a purchase raises is the purchase's own VAT-inclusive total, and that total is *derived* by `post_purchase` from the authoritative inputs — the proven-coherent per-UoM cost pair and the quantity in that UoM — using the application's own convention (`lib/purchaseMath.ts`: extend the per-UoM cost by the quantity, VAT is the gross/net difference). The client's declared line subtotal/VAT/total are cross-checks only and a disagreement is refused, so there is no second amount a caller could book debt with. The purchase, its lines, its movements, its stock and cost updates and its `supplier_ledger` row commit in one transaction, and a failure rolls back the purchase number with everything else. The pricing-pair check is a pre-pass that runs before the purchase number is consumed, so a malformed line leaves nothing behind at all.

A supplier invoice reference may be POSTED once per `(store, supplier)`. The canonical normalized form is `purchases.supplier_reference_key`, a generated column defined as `NULLIF(TRIM(UPPER(supplier_reference), char(9,10,13,32)), '')` — trim + uppercase, the same convention migration 002 uses for `product_barcodes.lookup_value`. A blank or whitespace-only reference normalizes to NULL and constrains nothing. The rule is enforced by `post_purchase` before a purchase number is consumed, and by `trg_purchases_no_duplicate_supplier_invoice_{ins,upd}` as the backstop. It is a trigger rather than a unique index on purpose: a database that already holds a duplicate could not have the index created over it, and the only ways around that would be to rewrite or delete a real financial document. The rule governs writes from now on; history stands as recorded.

**Both AP commands are idempotent on identity.** `purchases.id` and `supplier_ledger.id` are document identities the caller mints once. Replaying one with the same canonical content reconciles to the row that already posted — one payable, one stock receipt, one cost blend, no receipt or purchase number consumed — and replaying it with materially different content is a conflict. This is *technical retry* idempotency and is kept strictly separate from *business duplicate-invoice* detection: two genuinely separate deliveries under two identities are two purchases, refused only if they quote the same invoice reference, and two separate payments of the same amount are two payments.

**Supplier-ledger sign is the backend's, not the caller's.** Positive means the shop owes more. `purchase` → +, `payment` → −, `credit_note` → −, while `opening_balance` and `adjustment` are deliberately bidirectional and take the caller's sign (the Supplier screen has an explicit +/− toggle for adjustments). `post_supplier_payment` takes a positive `amountMagnitudeCents` and applies the direction itself, so a payment sent with the wrong sign still pays the balance down instead of adding to it; the legacy signed `amountCents` stays on the wire and its magnitude is honoured, its sign is not. `trg_supplier_ledger_sign_discipline` enforces the same convention against every other writer, and also that an entry is filed against the supplier's own store.

**Supplier payments may not create an advance.** Greaz models no supplier advance or receivable, so `post_supplier_payment` refuses a `payment` larger than the outstanding payable, reading that payable inside the posting transaction rather than trusting a displayed figure. Partial payments are supplier-level, not invoice-allocated. A negative balance stays reachable through the two explicitly-signed instruments — a `credit_note` the supplier issued, or a signed-off `adjustment` — which is what the Supplier screen shows as "credit on file".

**Supplier payments are not drawer events.** A `supplier_ledger` payment records an amount and nothing else: no method, no currency, no shift. `close_shift` therefore counts only `cash_usd`/`cash_lbp` sale tender, and WP-05 left it that way deliberately. Giving supplier payments a tender model is an open product decision.

**A return is not a negative sale.** A customer return is a CREDIT MEMO — its own document in its own tables (`sales_credit_memos`, `sales_credit_memo_lines`, `sales_credit_memo_refunds`, migration 011) — and the sale it reverses stands exactly as posted. Nothing is written back onto it: "not returned / partially returned / fully returned" is **derived** by summing the memo lines that point at it, and `sales.sale_type` / `sales.original_sale_id` stay unused, as migration 001 left them. Negative `sales` rows were not an option: `sale_items.quantity` is `CHECK (> 0)`, every `sale_payments` amount is `CHECK (>= 0)`, and every report, shift summary and drawer query filters `status = 'posted'` WITHOUT filtering `sale_type` — so folding returns into `sales` would have changed the meaning of all of them, with the wrong sign, on the day it shipped. Returns are layered additively instead: `dailySales`, `productSales` and `getSalesSummary` are untouched and still GROSS, and the returns series (`dailyReturns`, `productReturns`, `getRefundSummary`, `getRefundBreakdown`) sits beside them, so net sales and net profit are visible subtractions rather than figures that quietly changed.

**Every amount on a credit memo comes from the original posted snapshot.** The price, the VAT rate and amount, the discount allocation, the COGS rate, the tender the sale took and the exchange rate it locked are all read from `sales`, `sale_items`, `sale_payments` and the sale's own inventory movements. Nothing is recomputed from today's product price, today's VAT rate, today's cost pool or today's exchange rate: a refund settles a transaction that already happened, on the terms it happened on. Whether a line may be restocked is decided by whether the SALE produced an inventory movement, not by `products.is_service` as it reads now — a product reclassified since cannot make a service out of goods that left the shelf.

**A memo's share of each COMPONENT is a difference of two cumulative figures.** Rounding each return independently makes the parts disagree with the whole: three returns of one unit from a 3-unit, $10.00 line each round $3.3333 to $3.33, and the customer is a cent short for ever, because a posted memo is immutable. So a memo's share is `cumulative(already returned + returning) − cumulative(already returned)`, where `cumulative(q) = round(original amount × q ÷ original quantity)` — `posting.rs::prorated_cumulative_cents`, mirrored for the register's preview by `lib/creditMemoMath.ts::returnedLineAmounts`.

It is applied to the components the sale PERSISTED: the line's subtotal, its VAT and its discount allocation. **The total is derived as `subtotal slice + VAT slice`, and VAT is never a residual.** Taking VAT as `total − subtotal` was the original design and it is wrong: each of those series is monotone, but their difference is not, so the two roundings can move opposite ways on one step. An 11-cent, 3-unit line of 10 net + 1 VAT gives cumulative totals 4, 7, 11 against cumulative subtotals 3, 7, 10 — so the second unit's residual VAT is `3 − 4 = −1`, a credit note that ADDS output VAT, and the non-negative-VAT guard refused a return the customer was entitled to. Allocating the components separately fixes it at the root: both originals are non-negative, so both series are monotone and every slice is non-negative, and each lands exactly on its own original at full return, so their sum lands exactly on the line total. The one boundary left is money's own resolution — a line worth under a cent per unit has steps that credit nothing, so it is returnable in one go rather than unit by unit.

COGS is prorated the same way but against the cumulative RESTOCKED quantity, so a line returned once as a write-off and once to the shelf reverses cost for the second unit only.

**Returned stock comes back at the cost it left at, and the average is re-blended.** The restock movement carries the original sale's microcent COGS rate, and `cost::restock_weighted_avg` blends it into the pool at full precision. Leaving the average alone would put the units back in the quantity without putting their cost back in the value, so every subsequent average would be wrong by that much. Two states have no honest answer, both reachable only from a pre-existing negative pool (the POS permits selling below zero): a resulting quantity still ≤ 0, and a blend that would come out negative against the `CHECK (>= 0)` column. In both, the quantity still goes back and the existing rate stands. A write-off return (`return_to_stock = false`) moves no stock, writes no movement and reverses no cost — the margin on discarded goods is lost, which is the truth about them — and a service line can never restock at all.

**A refund goes back the way it came, and only that far.** A credit memo may refund only a `(method, currency)` pair the original sale actually took, capped in THAT currency's own unit — USD cents for a USD leg, whole lira for a lira one — NET of any change the sale handed back, and cumulatively across every memo of that sale. So a card-only sale cannot be refunded in cash (which would empty the drawer against a payment that never filled it) and a cash-only sale cannot be credited to a card that was never charged. The split need not be proportional. `store_credit` is not a refund method at all: Greaz has no customer-credit ledger, so it would be a liability recorded nowhere. The refund legs must sum to the memo total EXACTLY — there is no unpaid-credit instrument and no change on a refund — and a lira leg's USD equivalent is derived at the SALE's locked rate, never taken from the client.

**A cash refund is a drawer event; a card refund is not.** Expected drawer cash is now `opening float + cash in − change out − cash refunds out`, per currency, and `post_credit_memo` reads it inside its own transaction from the same `drawer_cash_for_shift` definition `close_shift` reconciles against. A cash refund that would drive the drawer below zero in its currency is refused, with no manager override: a refund the till cannot fund is a cash problem, not a permissions problem. A new credit memo must name an open shift of its store — checked after the idempotency resolution and again just before the commit, the WP-04 ordering — so a replay of a memo that already posted still resolves after its shift has been closed and counted.

**A return is idempotent on its identity.** `sales_credit_memos.id` is the return identity the caller mints once. Replaying it reconciles to the memo that posted — one refund, one restock, one cost blend, no credit-memo number consumed — and replaying it with materially different content is a conflict. The canonical comparison is over the request's INPUTS (which sale, which lines, how much of each, restock or not, the refund legs), because every amount is derived from those plus the history at the time, and by replay time the memo's own lines are part of that history. Two genuinely separate partial returns are two memos under two identities, subject to the cumulative quantity and tender caps.

**A checkout attempt is persisted BEFORE the request is sent, and posting refuses if it was not.** `post_sale` is idempotent on `sales.id`, which the client mints as the checkout identity, and that contract is the only thing between a lost response and a double charge — but it is only usable if the client can re-send what it sent. So the register freezes the complete canonical request into an attempt (`lib/postAttempt.ts`), writes it into the cart's own localStorage record, and only then invokes. The write goes through `lib/cartStore.ts::persistCarts`, which writes **synchronously and reads back**, and `runPost` refuses to invoke on a failed verdict. Both halves were broken: the attempt was written by mutating React state and letting a `useEffect` mirror it, so the effect ran *after* React committed while `salesRepo.post` was dispatched before `runPost` ever yielded — the invoke went first and the attempt reached storage afterwards, if at all — and the mirroring effect was `try { setItem } catch { /* ignore */ }`, so a full or blocked store meant posting proceeded with no attempt at all. A kill in that window left a cart with no attempt and no identity holding lines for a sale that may have committed; the cashier re-rings it, `post_sale` sees a new identity, and the idempotency contract never gets a chance to fire. The read-back is not ceremony: `setItem` throws on quota, but a store disabled by policy can accept a write and keep nothing, and comparing the exact string back out is the only check that covers that. It does not promise fsync — `lib/postAttempt.ts` states the durability envelope — only that the attempt is in the store before the request is on the wire. The guard is on the FIRST attempt only: once an attempt is durable, a later storage failure must not block the retry, because the identity is already committed and the sale may already exist. The mirroring effect stays best-effort for ordinary cart edits, deliberately: a lost edit costs a re-ring and can charge nobody twice.

**Greaz delivery: the driver collects, and the driver keeps the fee.** Orders arrive on WhatsApp, the cashier types them in, the shop assigns its OWN driver and agrees a delivery charge. The driver collects one amount from the customer — food plus delivery — keeps the delivery charge, and brings the food money back. There is no platform, no commission, no settlement and no external receivable; migration 014's deferred platform-AR design is **cancelled**, not postponed, because the confirmed process has no third party in it. Three numbers follow and the whole feature is about never confusing them: the **food total** is Greaz's sale (VAT applies, and it is what the driver owes from the moment the food leaves), the **delivery fee** is the driver's and never enters the shop, and **what the customer pays** is their sum — which exists only as a figure on a screen, because storing a total nobody owns is how it reaches a revenue report. The channel is relabelled "WhatsApp / Delivery" in the UI; the stored value stays `online_delivery`, since it is a reporting dimension with migration 014's history behind it and relabelling is presentation where renaming would be a restatement.

**`driver_collection` is a tender, not a channel.** A delivery order IS settled — just not into the drawer — so it is a `sale_payments` row, and the comparison with a card is exact rather than convenient: a card is money the shop will receive from a third party later, it is not in the till tonight, it settles the sale in full, and it is already a non-cash tender here. A driver collection is that, with the acquirer replaced by an employee. Keeping it in `sale_payments` is what preserves every existing invariant for free: tender must still cover the total (a delivery order is not "unpaid"), `is_cash_method` is unchanged so `close_shift` counts no drawer cash for it, the overpayment rule already refuses non-cash tender above the amount due, and a credit memo may refund only a `(method, currency)` pair the sale actually took — so a driver-collected order cannot be refunded in cash out of a till that never received any, and a counter sale cannot be credited to a driver who never carried it. The alternative, a sale with no payment row settled by a ledger entry off to the side, would have had to relax "tender covers the total", and then every drawer query, refund cap and reconciliation that reads `sale_payments` would be blind to how the order settled. Extending the `method` CHECK meant the documented SQLite table rebuild, which is safe for this table specifically: nothing references `sale_payments` or `sales_credit_memo_refunds` (both are leaves), the immutability triggers are dropped first and recreated in migration 012's symmetric form, and the copy is a column-for-column `SELECT` so no posted amount, method, currency or rate is re-derived.

**A driver receivable is raised by the TENDER, not by the total, and the fee is in neither.** `post_sale` sums the `driver_collection` legs and writes one `driver_ledger` `collection` row for that amount, in the same transaction as the sale, its lines, its movements, its stock and its tender — so there is no reachable state in which the food left the shelf and nobody owes for it, nor one in which a balance says a driver owes for an order that never posted. On an ordinary delivery that equals the sale total; on a part-prepaid one it is only the part he collects, and taking the total there would put money the shop already banked onto his balance. A delivery order may name a driver and raise NO receivable (a card-prepaid order still gets carried), and no zero row is written. Three coherence rules are enforced in `prepare_sale` before a receipt number is consumed, and again as migration 015 triggers so they hold for any writer: a `driver_collection` tender requires a driver, a delivery fee requires a driver, and a driver requires the delivery channel. The driver must be the store's own and still active for a NEW sale — checked after the idempotency resolution, so a replay still reconciles to its receipt after the driver who carried it has been retired. `driver_id` and `delivery_fee_cents` are part of the sale's canonical content, so a replay naming a different driver is refused as a CONFLICT rather than accepted and ignored — which would have left the receivable on the first man's balance while the screen believed it had moved.

**Driver settlements are a subledger, and the sign is the backend's.** `driver_ledger` is append-only, signed (positive = the driver owes the shop more), and the balance is `SUM(amount_cents)` — `supplier_ledger`'s design (migration 006) pointed the other way, down to migration 010's sign-discipline trigger. `collection` → +, `remittance` → −, `return_credit` → −, `adjustment` → ± with an explicit direction and a mandatory reason. `post_driver_remittance` takes the cash that physically arrived in its own currency's unit and DERIVES the USD equivalent at a rate it proves against the `exchange_rates` row, so a remittance sent with the wrong sign still pays the balance down; it is idempotent on `ledger_entry_id` (a retry reconciles to the row that posted rather than paying twice, and two genuine hand-overs of the same amount are two identities); and it refuses a remittance larger than the outstanding balance, read **inside the writing transaction**, which is what makes over-settlement and duplicate submission impossible under concurrency rather than unlikely. A `collection` or `return_credit` cannot be posted through it at all — those are consequences of a sale or a return and are written by the commands that post those documents, so a balance can never disagree with the receipts behind it. Unique partial indexes give one collection per sale and one credit per memo as the structural backstop. A retired driver may still remit: retiring him stops new orders, not settlement of old ones.

**A return on a delivery order credits the DRIVER, not the drawer.** The customer is settled by the driver out of the same cash he is holding, so a `driver_collection` refund leg writes a `return_credit` row reducing his balance and no drawer figure moves. Without the method the order would have been unrefundable and the pressure would have been to refund it in cash — money out of a till that never received any, with the receivable left on his balance in full. The cumulative per-method tender cap already guarantees returns cannot drive a balance negative. A return AFTER he has settled leaves the shop owing him, shown as credit on file, which is the truth about it.

**A remittance is not a sale, and the delivery fee is not revenue.** The revenue was recognised when the delivery order posted, so driver remittances are their own reporting series (`driverRemittances`) and are never summed alongside sales — the same separation the returns series has, and for the same reason: summing them would count every delivery twice. `sales.delivery_fee_cents` is outside every sale total, is never VAT-rated, is not a `sale_items` row (so it cannot reach COGS, inventory or margin) and is not in the receivable. `driverSettlements` reports balances as LIFETIME and delivery work and fees as PERIOD figures, and the column headings say which is which: a balance is not a period quantity, and a report showing only this week's rows would claim a driver still owed money he settled last week.

**Two things WP-6 deliberately did not decide.** (1) The **VAT and invoice treatment of the delivery charge** is an open question for Greaz's accountant. The charge is tracked and displayed, attributed to nobody's revenue and given no VAT rate, so either ruling can be implemented later without restating a posted row. (2) **Whether a remittance is a drawer event.** It records the currency and amount that arrived and the shift that took it, but it is NOT in the expected-drawer figure `close_shift` reconciles against — the same position WP-05 took for supplier payments. Expected drawer cash has one definition and every shift already closed was counted that way, so folding a new source of cash into it silently would change what a closed shift's variance means in a column that is immutable once written.

**A driver remittance IS a drawer event, and it needs a shift to land in.** Migration 015 left this as an open product decision; the owner has since confirmed that the driver returns the food payment to the cashier's normal cash drawer, so migration 016 settles it. A `remittance` must name an open shift of its own store (`trg_driver_ledger_remittance_needs_shift` — in migration 017's form, which is the one that actually checks `status`; plus `post_driver_remittance` refusing earlier with a friendlier message), and expected drawer cash is now `opening float + cash in + driver remittances in − change out − cash refunds out` per currency. The **native** amount is what the drawer counts — dollars as dollars, lira as lira — because that figure is compared against physical notes; the row's `amount_cents` is the USD equivalent and is what the driver's BALANCE moves by. A driver who collected $17.00 on a $15.00 order with a $2.00 delivery charge remits $15.00, and $15.00 is what the till expects: the $2.00 was never the shop's. `collection`, `return_credit` and `adjustment` are deliberately NOT shift-scoped — none of them moves cash, and an adjustment may be signed off outside trading hours. **Both readers of that figure must be kept in step:** a desktop walkthrough caught `ShiftSummary` showing $10.00 while `close_shift` computed $19.99, because the Rust definition had gained the remittance term and `shiftsRepo.getDrawerExpectation` had not. A cashier counting the till would have reported a $9.99 overage against an incomplete figure, so the term lives in both and the screen shows it as its own row.

**A refund on a delivery order must come from whoever is actually holding the money.** There are two sources and they are different pots: the driver, while he still has the food money, or the drawer, once he has handed it in. Which applies is read from his balance inside the posting transaction. While he holds it, a `driver_collection` refund leg reduces what he owes and the till is untouched — the automatic, determinable case, bounded by his outstanding balance and by `trg_driver_ledger_no_automatic_negative` (migration 016) as the engine's backstop. Crediting him beyond that would assert the shop owes him money it never took from him, and an append-only ledger could never unwind it.

**The drawer-funded refund path is DISABLED, because this application has no authorization.** Once a driver has remitted, the till is economically the right payer, and that path was implemented gated on a `manager_approval` string. That gate is not a gate: `users.role` exists in the schema with `('owner','manager','cashier')` and is read by **nothing**, there is no login, no session and no role check anywhere in Rust or TypeScript, and `activeContext` picks whichever `owner` row sorts first at boot. So the "approval" is a sentence the cashier types, and honouring it would let anyone at the till pay money out of the drawer against a receipt the drawer never collected — with an audit trail claiming a manager agreed. That is worse than not having the feature, because it manufactures the appearance of control. The path is therefore refused unconditionally (`substituting = false`, kept as an explicit constant so re-enabling it is one honest condition rather than a rewrite), the field is recorded on the memo as a note only, and the refusal tells the operator to record a signed-off driver adjustment instead. Re-enabling it requires an authenticated manager, server-side role enforcement, and an audit row naming them, in the same change.

**A remittance carries a frozen attempt, like a sale.** Now that it moves drawer cash, a lost answer costs twice: re-sending under a fresh identity would double a driver's balance movement AND make the till expect money that arrived once. So the drivers screen mints the `ledgerEntryId` ONCE, freezes the whole request, writes it to `localStorage` with a read-back proof BEFORE invoking, and refuses to invoke if that write cannot be proven (`lib/remittanceAttempt.ts`, `lib/remittanceStore.ts`). A synchronous gate drops a double-click in the same frame. Every failure is classified UNKNOWN — unlike `post_sale`, `post_driver_remittance` returns a plain `String` and there is no refusal envelope to key on, and matching on message text is what `classifyPostFailure` exists to refuse — so the operator is offered a read-only probe by identity rather than a blind retry. A persisted `posting` is promoted to `unknown` on restart, and a replay sends the ORIGINAL shift, not today's.

**A delivery order has ONE shape, and the backend decides it.** WP-6 validated coherence and left workflow to the register, so `post_sale` also accepted a delivery order part-settled by cash or card, or named by no driver at all; the gap was documented as safe because no cashier-facing path reached it. That is an argument about one screen, not about the data — `post_sale` is also reached by a replayed payload, a future screen, an import, a script and a second terminal, and the shape it accepts is the shape the database can hold. Settled at the till means the drawer expects money that is in a driver's pocket; no driver means food left the shelf with no balance saying who owes for it. So a NEW `online_delivery` sale must name an active driver of its own store and be settled by `driver_collection` legs ONLY, summing to the food total exactly (the fee is his and is in neither figure). Checked in `post_sale_tx` AFTER the idempotency resolution — a historical part-prepaid row still replays to its own receipt — and BEFORE the receipt number, so a refusal costs the sequence nothing. The register still permits only that shape too: delivery REQUIRES a driver (without one the auto-pay path would turn a blank tender into cashier cash), the tender is derived from channel + driver rather than toggled, assigning a driver clears any typed tender, and `buildFrozenRequest` ignores the cash inputs entirely — pinned by its own tests, including a cart PERSISTED with cash that still posts as a driver collection alone.

**The checkout barrier compares the IDENTITY and the frozen request, not the presence of an attempt.** `lib/cartStore.ts` refuses a mirror write that would drop an attempt storage is holding, but asking only "does the incoming cart still have one?" left two writes through. A stale effect carrying an OLDER valid attempt (a cart holds two in a session — one settles, the cashier re-rings) replaced the live identity with a settled one, so the identity on the wire was the one NOT in storage. And `allowDropFor` was keyed by CART ID, which outlives any number of checkouts, so a permission minted when attempt #1 settled authorised deleting attempt #2. The barrier now compares the `checkoutId`, the frozen request by value (structurally, so a JSON round trip's key order cannot read as a move), and the direction of the outcome — `posting` → `unknown` only, never back. Retirement permission is a map of cart id → the identity retired, minted inside the state updater that retires it, where the live attempt is readable. `requireAttemptFor` takes `{ cartId, checkoutId }` and proves THAT identity landed, so a posting path serialising a stale array cannot satisfy it and then invoke under another id.

**A remittance needs an OPEN shift, and a return credit needs its own return** (migration 017). 016 required a remittance to name a shift of its store but not an open one — and a closed shift's `expected_cash_*` and variances are computed once, in the transaction that closes it, and immutable after (009). So cash could land in a shift nobody will recount, against a variance already written. And 015 proved a COLLECTION's source (`related_sale_id` must name a sale whose own `driver_id` is this driver) but proved nothing about `related_credit_memo_id`, so a `return_credit` could write down any driver's balance against any memo: another driver's, another branch's, or a counter sale's. The caps bound the SIZE of a credit, never whose return justifies it, and the ledger is append-only, so a row against the wrong document can only be offset by one that misstates something else. The reachable case is a memo with no automatic credit — a delivery memo always carries one and the one-credit-per-memo index blocks a second, but a memo whose refund took no `driver_collection` leg had nothing guarding it. 017 therefore replaces the shift guard (DROP then CREATE: a v16 database already carries the weak one and `IF NOT EXISTS` would keep it) and adds a return-credit source guard proving the memo's store, its sale's driver, and that any `related_sale_id` is the memo's own. Both are BEFORE INSERT, so history stands.

**A remittance replay compares its attribution too.** `CanonicalDriverEntry` covered the money and stopped there, leaving the shift, the exchange-rate row, the recording user and the device outside the comparison — so a retry arriving with any of them changed was accepted as faithful and the caller told its own claim had posted, while the row went on naming the first set. The shift is the one with money attached: the cash would stay expected in the first till with a screen saying otherwise. All five are compared now; a faithful replay still reconciles.

**An approval string is a CLAIM, and the audit trail says so.** A memo carrying `managerApproval` was annotated `[Manager decision] …`, which asserts in an immutable financial document that a person with authority decided something when somebody typed into a box. Nothing here can authenticate a manager (see the disabled drawer-funded path above), so the field is still accepted and still recorded — the operator's words are worth keeping, and refusing a customer's refund over a note would be worse — but under `UNVERIFIED_APPROVAL_PREFIX`, which names the claim and its limit. When an authenticated manager, server-side role enforcement and an audit row naming them arrive in one change, that change replaces the prefix with a reference to the audit row.

**A closed shift's reconciliation is HISTORY, not a live calculation.** `close_shift` computes `expected_cash_*` and both variances inside the transaction that marks the shift closed, writes them once, and `trg_shifts_no_update_after_close` (migration 009) makes them immutable. The figures were therefore always right and always unreadable: the Shift screen showed the open shift or the form to open one, so the moment a cashier closed a shift the counted cash, the expected cash and the variance they were held to left the visible application. WP-A1 adds a second tab that reads them — `shiftsRepo.listHistory` / `getHistoryDetail`, composed from the SAME five shift-scoped accessors the live view uses, because two query paths for one set of figures is how a screen comes to disagree with itself. For a closed shift the stored columns are the answer and are never re-derived; for the open one there is nothing stored yet, so the live figure is labelled a running total. The distinction matters because the expected-cash FORMULA has changed twice — WP-06 added cash refunds out, WP-7 added driver remittances in — so a shift closed before either change was closed, correctly, on the formula of its day. Recomputing it now would silently restate a variance the cashier was never shown. So the panel states the recorded figure and, when today's components do not reproduce it, says so in a line of its own rather than choosing one of the two numbers and hiding the disagreement. No current exchange rate is read anywhere in the path: every drawer term is native, and a lira tender's USD equivalent was computed at the rate the SALE locked and stored on the payment row.

**Both of that panel's loaders are LATEST-REQUEST-ONLY.** They are async and they are re-run by ordinary interaction — a date typed into a filter, a store switched underneath, one row clicked and then another — so two answers are in flight at once routinely and nothing promises they return in order. Writing each one into state as it landed meant the SLOWER answer won: the previous store's shifts under the new store's name, or a reconciliation belonging to a row nobody has open. Each loader now takes a monotonic generation before it awaits and compares it after, and a superseded request writes NOTHING — not the rows, not the error, and not the loading flag, since an old request clearing the spinner says "loaded" over a list still being fetched. The effects bump the generation on cleanup, so a dependency change or an unmount retires whatever is in flight, and a new store or filter window also retires the open detail, because the row it belongs to may not be in the new answer. Pinned by deferred-promise tests that resolve the responses deliberately out of order (`tests/unit/shiftHistoryRaces.test.tsx`).

**A kitchen note is a per-line snapshot that carries no money.** "No pickles" on one of two identical burgers is a fact about what the kitchen was told, in exactly the sense `product_name_snapshot` and the unit price are, so it is a column on `sale_items` (migration 018) and not a child table: a column inherits migration 012's seal for free, and `trg_sale_items_no_update` already makes a posted note as immutable as the price beside it. It touches no total, no VAT figure, no discount allocation, no COGS rate, no inventory movement and no receivable, and no posting command reads it to decide anything — a PAID modifier (extra cheddar, a large upgrade) is a priced `sale_items` row of its own and stays one, because the moment free text starts carrying money the receipt stops reconciling to its lines and nobody can say which notes were charged for. It IS part of the sale's canonical content, so `CanonicalLine` compares it and a retry carrying a different instruction is refused as a CONFLICT: nothing can edit a posted line, so a difference accepted silently would be permanent, with the caller told its instruction had posted while the stored line, the kitchen ticket and the receipt all still said something else. `""` and NULL are ONE value — `posting.rs::normalize_kitchen_note` and `lib/kitchenNote.ts::normalizeKitchenNote` perform the same reduction on both sides of that comparison, and migration 018's `TRIM(...) <> ''` CHECK keeps any other writer to it — because otherwise a client serialising an untouched line as `""` would turn a faithful retry of an ordinary order into a conflict. The length bound (200) is in the CHECK and in `prepare_sale`, counted in CHARACTERS, because SQLite's `length()` counts characters for TEXT and the staff type Arabic at two bytes a letter.

What the SQL actually enforces is worth stating exactly, because an earlier draft of this file implied more. The CHECK is `kitchen_note IS NULL OR (TRIM(kitchen_note) <> '' AND length(kitchen_note) <= 200)`. It therefore forbids exactly two things: a value that is empty or entirely whitespace, and one longer than 200 characters. It does NOT normalise: it does not trim on the way in, it does not touch leading, trailing or interior whitespace, and `" no pickles "` is a perfectly legal stored value as far as the engine is concerned — it will simply never compare equal to `"no pickles"` on replay. Canonical form is the application's job on both sides (`posting.rs::normalize_kitchen_note`, `lib/kitchenNote.ts::normalizeKitchenNote`), and the CHECK is only the backstop that stops a third writer storing a second spelling of "no instruction". `length()` counts characters for TEXT, so the 200 is characters and Arabic is not penalised for its two bytes a letter.

**The note is authoritative from the first keystroke, because F5 does not blur.** The editor first held the text as a local DRAFT and committed it on Enter or on blur, to save a cart write per keystroke. Post is also a window-level F5 handler, and a keyboard shortcut blurs nothing: pressing it with the caret still in the box posted the sale carrying the line's OLD note while the cashier was looking at the text they had just typed. The posted line is immutable, the kitchen ticket prints from the posted sale, and nothing afterwards could put the instruction back. So every keystroke now updates the cart's own note through `setLineNote`; there is no uncommitted state left to lose, and the locked-cart choke point refuses an edit to a frozen line exactly as it refuses a quantity change. The cart holds the text EXACTLY as typed while the editor is open — trimming per keystroke would eat a trailing space under the caret — and the trim happens once when the editor closes, with `buildFrozenRequest` and the merge rule normalising again, so an untrimmed value can never reach a posted row. Escape is an explicit reversal to the instruction the editor opened on, and a cart that locks mid-edit closes the editor rather than leaving a caret in a box whose text can no longer be committed.

**The cart's merge rule includes the note, and that is what makes the feature work.** Adding a product used to merge on `(product, selling unit)`; it now also requires an equal normalised note (`kitchenNotesMerge`). Without that, clicking the tile a third time would fold a plain burger into the line marked "no pickles", the kitchen would make three of them wrong, and nothing on the receipt would show what had been asked for. The consequence is deliberate: a tile click lands on the first line with NO instruction, so the way to get two different notes is to note the first line and click again, and a note therefore applies to a whole line — all three of a line of three. The note is frozen into the posting request with everything else, and a locked cart refuses a note edit through the same `setLines` choke point that refuses a quantity change, because a note typed under a live attempt would turn the one recovery path into a conflict.

**The kitchen ticket is a separate document from the receipt, and shows no money.** A receipt is a financial document and has to show the money; a kitchen ticket has to show the FOOD, at a size readable across a hot room, and must not show a price at all — a price on a prep ticket is something to be read out, queried and mistaken for a total. So `KitchenTicketPrint` prints quantity, item and instruction, plus the receipt number (what the pass calls out, and what matches the customer's copy) and the channel and driver (a delivery ticket is packed differently). It is printed FROM the posted sale by identity, never from the cart: a ticket for an order that might not exist is worse than no ticket. Unlike the receipt it is localised, because the kitchen staff read Arabic. Exactly one print root is ever mounted — `#receipt-print-root`, `#kitchen-ticket-print-root`, `#shift-report-print-root` — because `@media print` in `index.css` reveals whichever is present, so two mounted roots would emit two documents; `PosRegister` mounts the one the operator asked for and fires `window.print()` from an effect, after the commit, since the choice is React state and the DOM only carries it after the render.

**The delivery panel collapses; its FIGURES do not.** WP-6 gave the register a driver select, a fee input, a full-width tender block and two explanatory paragraphs, permanently, on every delivery order — roughly 115px of the one region a 1366x768 till is short of, long after the cashier had chosen the driver. WP-A3 folds the CONTROLS to a one-line summary (the tender as a compact chip, the driver, the fee, and an Edit button) once the arrangement is DECIDED — a driver chosen, a charge entered, nothing refused — and forces them open until then, the same rule the discount panel follows: a control the cashier has to use is never behind a disclosure. The four figures never fold, because they are what the cashier reads to the customer. The financial behaviour is untouched: same `deliveryTotals` split, same derived tender, same `buildFrozenRequest`.

**Folding is a decision about the SCREEN, so a SESSION decides it, not a verdict recomputed per render.** WP-A3's first version derived "collapsed" from the arrangement itself, and the arrangement is re-read on every keystroke: typing a $2.50 charge made it parse at `2`, so the controls unmounted with the caret still in the fee box and the order went out at $2.00 unless the cashier noticed and reopened the editor. The state is now an explicit edit session (`deliveryEditCartId`), keyed by CART ID because the register holds several and a session opened on one must not describe another. It opens when the panel is forced open for an undecided order or when Edit is pressed, and it ends only on a deliberate completion — the Done button, Enter in the fee box, or focus leaving the panel — and then only while the arrangement is actually decided, so Enter on `2abc` or with no driver leaves the controls and the refusal where they are. A blur whose `relatedTarget` is inside the panel is a Tab between its own controls and keeps the session; a blur to nowhere (alt-tab, a print dialog) keeps it too, because neither is the cashier saying they are finished. Pinned by interaction tests that type the fee one character at a time and assert the panel after every one, and confirmed on the desktop with real key events.

**On a driver-collected order the payment panel says what is true, not what the till usually says.** "Total paid $0.00" and "Remaining $9.00" were both wrong in the same way: the order IS settled — the driver has taken responsibility for the money — and nothing is outstanding at the till. So the two rows are "Cashier receives now" ($0.00) and "Driver owes Greaz" (the food total). The receivable is named, rather than inferred from the absence of a figure.

**The receipt states what the customer paid the driver BESIDE the invoice, never inside it.** `sales.total_incl_vat_cents` is Greaz's own sale with Greaz's own VAT in it; the delivery charge is the driver's, has no VAT rate, is in no sale total, no inventory movement and no receivable, and its fiscal treatment is STILL UNCONFIRMED by the shop's accountant. So a delivery receipt carries a visibly fenced-off supplementary block — "this invoice (food)", "delivery charge (driver's)", "customer paid driver" — with wording that claims no VAT treatment and says the treatment is pending confirmation. The $9 invoice stays a $9 invoice; the $11 is stated as a fact about the evening. `customerPaidCents` is computed at render and stored nowhere, exactly as on the register: a total nobody owns is how a figure like it reaches a revenue report. When the accountant rules, the ruling is implemented as a migration plus a posting change — not by editing this block.

**The importer configures a MENU, not just a catalogue.** The first Greaz import created all sixteen items correctly and left every one of them with no section, no glyph and no description, so the register grouped the whole menu under "Other" and somebody opened sixteen product forms by hand to fix presentation data the spreadsheet already knew. `menu_category`, `icon` and `description` are now read — OPTIONAL columns, because making them required would reject every file written against the old template and a product with no section has always been valid (migration 013 leaves both columns nullable on purpose). The section is VALIDATED against `MENU_CATEGORIES` rather than accepted as free text: `resolveCategory` maps anything unknown onto "uncategorised" for display, so an unvalidated import would silently park a typo'd "burgerz" in Other, which looks exactly like having forgotten to categorise it. The glyph goes through `isSafeIcon` — bounded at four code points, no control or bidi-override characters (ZWJ stays legal, it is how a composite emoji is built), no markup and no leading `=`/`+`/`@`, since a cell starting with `=` is a formula to every spreadsheet that reads the catalogue back out. Both write through `productsRepo.save`, so the spreadsheet path and the Products form normalise identically. Every pre-existing constraint stands: a VAT rate must be chosen, a stocked product still needs a barcode, SKUs and barcodes are still unique in the file and against the database.

**A row's `active` flag is now actually persisted, and the preview says what each row will become.** The column was read and parsed onto the validated row, and then left out of the save call — and `ProductSaveArgs.isActive` is optional and defaults to true, so every imported row landed SELLABLE, including the ones a shop had deliberately marked inactive. Nothing on the preview contradicted it, which is why a desktop walkthrough did not catch it: the table showed the name, price, VAT, units and section and said nothing about sellability or stock classification. Both are a column now (Active/Inactive and Stocked/Service, as RESOLVED values, so the defaults a blank cell takes are visible rather than remembered), and the dialog passes `isActive` through. The three layers are pinned separately, because only the last one is persistence: the parse (`tests/integration/productImport.test.ts`), the preview and the save arguments (`tests/unit/productImportDialog.test.tsx`), and the row the command actually writes (`src-tauri/src/tests/catalog.rs`, against a real database).

**Every cell is validated in FULL, never by numeric prefix.** `parseFloat` and `parseInt` read a leading number and stop, so `2abc` imported as $2.00, `12abc` as 12, `2.5` in a whole-number conversion field truncated to 2, and an unrecognised boolean token silently took the column's default — `active: maybe` became a sellable product. A typo did not fail the import; it imported something plausible and wrong, and the preview showed it as a valid row. Prices now match the application's own money shape (digits, at most two decimals, a leading `$` and well-formed thousands groups stripped first) and three decimals are refused rather than rounded, because an import is not where a rounding rule should decide a margin. Quantities must be whole numbers. Booleans accept exactly `yes/true/1/y` and `no/false/0/n`, case-insensitively, and ANY other non-blank token is an error naming the row and the accepted values. A BLANK cell still takes the documented default (active, not a service), which is the backward-compatible half of the contract: a file written against the old template still parses, still validates and still imports.

**A migration is not a development fixture: migration 019 retires the v3 demo catalogue.** Migration 003 inserts three products — "Coffee 250g", "Bottled Water 1.5L" and "Wholesale Olive Oil 5L" — plus four barcodes into EVERY database the application creates, and migration 004 gives them five `product_uoms` rows. 003 says so in its own header: it exists "so dev environments come up with usable data". But migrations run on every installation, so a restaurant opening Greaz for the first time was handed three sellable grocery items on the register's menu grid, scannable and rung up onto a customer's receipt. 003 has shipped and cannot be edited — its checksum is recorded in every database that applied it, and changing it would stop those databases opening — so 019 corrects the state additively instead.

**It sets `is_active = 0`, by primary key, and only on a row it can prove is an untouched original.** Deactivation rather than deletion, because a product is referenced by every document that ever used it and `is_active = 0` is the supported way to say "not sellable" (`listEnriched` and `findByScan` both filter on it). Nothing is deleted, no child row is written, and no historical document is touched.

The predicate is the whole safety argument, and the first version of it was too weak in two ways. It matched `id IN (...) AND sku IN (...)`, which is not a pairing — a row whose id is `…d1` and whose SKU is `DEMO-003` satisfied both lists — so each statement now names ONE id and ONE SKU together. And it checked only stock, SKU and transactions, which does not mean untouched: an owner can rename a product, reprice it, give it a section, an icon, a description or a reorder point, change its VAT rate or pricing mode, make it a service, add a barcode or retire a UoM without ever selling one, and every one of those is somebody adopting the row. So the predicate now compares the COMPLETE mutable signature at the v18 shape — name, description, VAT rate, pricing mode, both prices, both cost pairs (cents and microcents), quantity on hand, reorder point, `is_active`, `is_service`, category and icon — plus the barcode and UoM sets as EXACT sets: the child count must match and every expected child must still exist with every column intact, which is what proves none was added, deleted or modified.

Schema drift between 003 and 018 is accounted for rather than assumed: `products.unit` was in 003's INSERT and was dropped by 004, so it cannot be compared; `avg_cost_*_microcents` arrived in 008 and are 0 for a seed row; `category` and `icon` arrived NULL in 013; `product_uoms` did not exist before 004.

`updated_at = created_at` is required too, on the product and on every child, and its semantics are proven rather than assumed: all three tables carry an unconditional AFTER UPDATE trigger that rewrites `updated_at` (`trg_products_updated_at` from 001 and recreated in 008, `trg_product_barcodes_updated_at` from 002, `trg_product_uoms_updated_at` from 004), so any UPDATE by any path bumps it and an unequal pair PROVES the row has been written. The converse is not claimed, which is why it is an extra condition and not a substitute for the signature. The one writer that bypasses the trigger is 008's microcent backfill, which drops it deliberately and does not write `updated_at` at all.

The transaction guards stand on top of all of that: a `sale_items`, `purchase_items`, `inventory_movements` or `sales_credit_memo_lines` row naming the product leaves it active whatever its columns say. **Anything that cannot be proven pristine stays ACTIVE** — a stale demo item is a tidiness problem the owner fixes in one click, while deactivating an adopted product is a stock item disappearing from the till mid-service. Re-running changes nothing, because `is_active = 1` is part of every predicate.

A test that WANTS a demonstration catalogue calls `test_support::activate_demo_catalogue`: a development fixture is created by the thing that needs it, in one visible call, and production provisioning creates nothing sellable. The rule is asserted from both sides — a fully migrated virgin database has zero active products (`src-tauri/src/tests/migrations.rs`, `tests/integration/virginDatabase.test.ts`) — and every "adopted" case above has its own test proving the row survives.

**A retired product still reserves its barcode, and the importer now says so.** `UNIQUE (store_id, barcode)` (migration 002) is on the barcode row and takes no notice of whether its product is active, so a value held by a deactivated product — including the three 019 retires — is still taken. The importer used to report that as "Barcode already exists in the database", which is true and useless: the operator could not find the product anywhere, because the Products page lists only active rows. The message now names the owning product and its SKU, says whether that product is ACTIVE or INACTIVE, and in the inactive case tells the operator to tick "Show inactive" on Products and reactivate it — which is why that checkbox exists. Nothing is reactivated automatically, no barcode is ever moved between products, and no barcode row is deleted to free a value: a barcode belongs to a product that history may reference, and deleting it to satisfy a constraint would be destroying evidence for tidiness.

**An invalid EAN-13 check digit is an ERROR, and every refusal carries its own reason.** It was a warning, and a warning row is not imported — so the product was silently absent and the summary reported it as "skipped because its SKU already exists", a clash that had not happened. Each issue now carries a code (`invalid_barcode_checksum`, `duplicate_sku_in_file`, `duplicate_barcode_in_file`, `sku_exists`, `barcode_taken_by_active_product`, `barcode_taken_by_inactive_product`, `malformed_row`), the preview counts READY / REJECTED / SKIPPED as three different outcomes with a per-reason breakdown beneath them, and the final summary reports created, skipped and rejected separately. `sku_exists` is the only code that is a skip; everything else is a refusal.

**A menu item's cost can be TYPED, and it is a property of the item (WP-B1).** Greaz could value things it BUYS AND COUNTS and nothing else: the only writer of `products.avg_cost_*` is a purchase, a burger is not purchased, so every prepared item was either a stocked product nobody ever bought (cost 0) or a service (cost 0), and both reported a 100% margin. The demonstration menu's own test said so. Migration 020 adds `products.costing_method` — `'purchase_average'` (the default, and the behaviour every existing row already had) or `'standard'` — plus `products.standard_cost_excl_vat_microcents`, the typed figure, and `standard_cost_set_at`. The PRODUCT's method decides first; only under `purchase_average` is the SALE's `cogs_method` (weighted average vs last purchase) consulted at all. That ordering is the whole posting change, and it is why two settings that look alike do not fight: one is a property of the item, the other of the till.

The typed cost is a RATE in microcents, like `avg_cost_*`, because a unit cost is money per base unit and can legitimately sit below a cent. It is stated EXCLUSIVE of VAT and has no inclusive sibling and no rounded cents mirror: every COGS figure any report reads is net, and deriving an inclusive one would mean choosing a VAT rate for a cost with no document behind it. `post_sale` reads the figure from the DATABASE inside its own transaction — there is no field for a cost on the wire, so no cashier-controlled request data can set one — and extends it the one documented way: precise rate times base quantity, rounded once at `extended_cost_cents`.

**`NULL` is not zero, and the difference is the point.** `NULL` means no cost has been configured; `0` means the owner asserts the item costs nothing. So the column is nullable with a `>= 0` CHECK rather than `NOT NULL DEFAULT 0`, which would have answered the question for the whole catalogue with no way afterwards to tell an assertion from an omission. Selecting Manual Cost without stating a figure is REFUSED — by `save_product`, by `trg_products_costing_coherence_{ins,upd}`, and by `post_sale` as defence in depth — never defaulted. Refusing at the till is deliberate and debatable: the alternative is how a restaurant acquires a year of 100% margins and no way to date the start of it.

**A zero cost is only `purchase_average` if a DOCUMENT says so.** `'uncosted'` covers two routes to the same zero, and the second was WP-B1's own defect. A service on purchase valuation can never acquire a basis — the only writer of `avg_cost_*` is a purchase — and was named `uncosted` from the start. A STOCKED product with a zero average was not: it was stamped `purchase_average`, and reporting reads that as a verified answer, so revenue nobody had ever costed was counted inside the costed share and printed a 100% margin the coverage panel then certified. A zero average is two different facts wearing one figure — goods received at a stated cost of nothing (a free case, a sample, an opening count valued at zero), whose $0.00 is an answer; and a product that has never been purchased, whose $0.00 is the absence of one — so `post_sale` now resolves it against PERSISTED EVIDENCE: an `inventory_movements` row of type `purchase` or `opening` for that product and store, the same pair the weighted average is built from and the `last_purchase` resolution already reads. Found, the zero stays `purchase_average`; not found, the line is `uncosted`. Deliberately NOT evidence: `quantity_on_hand` (stock arrives by adjustment too, and an adjustment is valued AT the average and never moves it, so it states no cost), the zero itself, and a `sale`, `return_in` or `adjustment` movement — each carries the rate it inherited from the pool, so treating one as a basis would let an uncosted sale certify its own successors. A NONZERO average is never probed: the average IS the valuation. Nothing about the money changes — same rate, same `extended_cost_cents`, same movement row, same stock decrement, same weighted average — and the probe only runs when both average columns are zero, so the correction reclassifies only what it can show has no basis at all. The decision is forward-only like every other cost input: a product that acquires a receipt costs its NEXT sale from it, and the `uncosted` line already posted stands, because `sale_items` is sealed.

**Manual cost is restricted to NON-STOCK items, and that is a financial argument.** (WP-B2-B restricts recipe costing the same way, for the same reason.) For a stocked product the COGS rate is not merely a reporting figure: it is written onto the sale's `inventory_movements` row, and that ledger is what makes stock auditable — `quantity_on_hand` and `avg_cost_*` are maintained together precisely so the quantity and the value of the shelf agree. A manual rate there says the goods left at one price while the pool they left from says another, and `inventory_movements` is append-only, so nothing could ever unwind it. A service line writes no movement, decrements no stock and touches no pool, so there is no second figure to contradict — which makes the service case financially closed and the stocked case financially open, and B1 ships only the closed one. A restaurant's prepared items ARE the service case; valuing stocked goods from a recipe of counted ingredients is WP-B2/B3's job, and it is the right answer there because the cost arrives WITH a consumption document.

`'recipe'` was put in migration 020's CHECK and refused by the same trigger pair. SQLite cannot ALTER a CHECK, and widening one on `products` — referenced by `sale_items`, `purchase_items`, `inventory_movements`, `product_uoms`, `product_barcodes` and `sales_credit_memo_lines` — would be the most dangerous statement this codebase could run, for one enum value. So the DOMAIN was stated once up front and the IMPLEMENTED SUBSET left as a trigger, which WP-B2-B's migration 022 drops and recreates exactly as 017 replaced 016's shift guard — and the CHECK itself is untouched to this day, which is the whole return on that decision.

**A posted line now records WHERE its cost came from.** `sale_items.cogs_source` is `'standard'`, `'purchase_average'`, `'last_purchase'`, `'uncosted'` (no cost basis existed — today's silent zero, finally named) or `'recipe'` (reserved). `NULL` means the line was posted before the column existed, which is the truth about it: no posted row was rewritten. It is PROVENANCE, not arithmetic — nothing derives a total from it and no posting command reads it to decide anything — and it is NOT part of the sale's canonical content, because the backend derives it from the product row, so a replay cannot carry a conflicting value. It records what ACTUALLY supplied the rate: a `last_purchase` sale that fell back to the average is recorded as `purchase_average`, since a provenance column that could lie is worse than none.

**Switching a costing method is FORWARD-ONLY.** It changes what the NEXT sale snapshots and never restates one already posted — already true of every cost input here (change an average today and yesterday's receipts keep their COGS), and `sale_items` is sealed by migration 012, so the alternative does not exist. A replay resolves AFTER the idempotency check, so a till that lost an answer still gets its own receipt back even when the product has since been reconfigured into a state that would refuse a fresh sale. `standard_cost_set_at` moves only when the FIGURE moves: an ordinary edit must not restamp an eighteen-month-old plate cost as stated today, which is what stops it looking like a number worth doubting. There is deliberately no `standard_cost_set_by_user_id` — this application has no login, no session and no role check, so such a column would record a guess while LOOKING like attribution, the defect `UNVERIFIED_APPROVAL_PREFIX` exists to name. A timestamp is a fact; an author here would be a claim.

**A return on a manual-costed line reverses revenue and no cost.** Nothing changed, deliberately: whether a line may be restocked is decided by whether the SALE produced an inventory movement, and a non-stock line produced none. So a manual-costed return restocks nothing, reverses no cost and blends nothing into any pool — the margin on food already made and discarded is lost, which is the truth about it — and no ingredient movement is invented in its place.

**A gross-profit figure is published WITH its cost coverage, and coverage asks TWO questions.** `reportsRepo.cogsCoverage` buckets a period's posted lines by `cogs_source` and `lib/reportMath.ts::costCoverage` turns that into shares of REVENUE — revenue, not line count, because ten uncosted sides matter less than one uncosted platter and it is the money that reaches the margin. The first cut asked only "does this line name a cost source?" and printed the answer under a label about having a cost, and for a line posted before migration 020 those are different questions with different answers. Its provenance is `NULL` and always will be — history is not restated — but the COGS figure it was posted with is sitting in the row, and that figure is what every gross-profit number here is already built from; calling it uncosted claimed money was missing from a calculation that was complete, and warned that profit was overstated when it was not. So the panel reports COST-BEARING revenue (a recorded source that is an answer, OR a legacy line with a nonzero COGS snapshot) and, as a subset of it, VERIFIED-SOURCE revenue (the share whose origin is recorded and traceable). A legacy costed line sits inside the first and outside the second, labelled as exactly that — never relabelled `purchase_average` or `standard`, which would invent a provenance for a posted document. MISSING COST is the union of two states and is the only thing that CAN overstate the profit above it: a line whose source says nothing was configured (`uncosted`), which is a to-do list the owner can work through on Products today, and a legacy line whose snapshot is ZERO, where nothing distinguishes "cost of nothing" from "nobody said". A deliberate `standard` zero is cost-bearing on its SOURCE and not its figure, because the owner asserting an item costs nothing is an answer. ESTIMATED (a figure somebody typed) stays a separate row from DOCUMENTED (a rate derived from a purchase invoice), since they are different claims. The missing-cost figure is REVENUE, not the cost those lines are missing — what they should have cost is the unknown itself — so the warning says the profit MAY be overstated and never quantifies the overstatement from a sales figure, which would be a number with nothing behind it. Both shares divide by the same denominator, the period's gross sales excluding VAT, so the verified share is a share of GROSS SALES and not of the cost-bearing subset: dividing by the subset would print a confident 100% for a period whose costs are mostly untraced, and both labels name the denominator rather than reading as a nested breakdown. `isVerifiedCostSource` and `isCostBearingLine` are the two predicates, kept apart by name so the conflation cannot come back; Sales History colours a line as a gap only when it is not cost-bearing, having previously flagged legacy lines whose real COGS rate was printed in the cell directly above. Greaz has printed a 100% paper margin on food since it shipped, and a profit number without this beside it is indistinguishable from one that is simply wrong. The buckets are the same lines `productSales` sums, scoped the same way, so the panel cannot disagree with the cards above it — and the basis is therefore GROSS sales before returns, while the gross-profit card beside the panel is NET of returns (`netSales - netCogs`), so neither share is a percentage of that card. The panel says so in a note of its own: a returned line was still costed or not costed when it was sold, so excluding returns would answer a different question, but a share a reader may mistake for the net one has to say which it is.

**What WP-B1 does NOT solve, stated plainly.** A cost field is not restaurant inventory accounting: it gives a believable margin per item and tells the owner nothing about losing chicken, because nothing is counted. There is no labour, no overhead, no wastage event and no stock-take variance, so a "food cost %" from this is an ingredient-cost percentage at best. A standard cost that drifts from the purchase average is not reported as a variance — it is simply a different number. And a manual cost is an assertion by whoever is at the till, because the authorization gap is unchanged.

**A RECIPE is a definition, and in WP-B2-A it sold nothing (migration 021).** `recipes` is a versioned header per product and `recipe_components` its ingredient lines, and that was the whole of B2-A: an owner could author a recipe, see what it costs, version it and publish it, and **no product could select `costing_method = 'recipe'`** — migration 020's `trg_products_costing_coherence_{ins,upd}` pair was left standing, untouched, and refused it exactly as before, while `post_sale` was not modified and could not reach either table. That split is what made B2-A unable to misstate a single posted figure, and it was asserted rather than assumed: `migration_021_leaves_the_recipe_costing_refusal_in_place` pins it to version 21 specifically, through `migrate_through(21)`, because an assertion that migration N does not relax a rule silently becomes an assertion about N+1 the day N+1 arrives. **WP-B2-B (migration 022) is that N+1** and is described below: it replaces the trigger pair and teaches `post_sale` to honour a recipe. No ingredient stock moves in either step, and there is still no `consumes_stock` column at all — a column with no reader is a promise the engine has not made. Consumption is WP-B3, with its own command, its own movement rows and its own return semantics.

**A recipe quantity is an exact reduced FRACTION, and it is costing-only.** `sale_items.quantity`, `inventory_movements.quantity_delta` and `products.quantity_on_hand` are INTEGER, and `lib/uom.ts::parseQuantityInput` refuses a typed decimal that does not land on a whole base unit — right for a sale, since half a box of twelve is not something you hand over. A recipe cannot live under that rule: "150 g of beef" is fine when the base unit is the gram, but "half a bun" is not an integer count of buns at all, and rounding it to 0 or 1 is a 100% costing error on that line. So `recipe_components.quantity_num / quantity_den` stores it exactly, which also covers `1/3` and not merely `0.125`, and which is the convention `product_uoms.factor_num / factor_den` already uses for the same job. **This is safe in B2 for one specific reason that B3 cannot borrow: a recipe quantity is only ever a multiplier on a cost RATE.** It is never a quantity of anything that moves, no `inventory_movements` row is written from a recipe, and so no fractional base quantity ever has to reconcile against an integer column. WP-B3 will have to decide what half a bun does to an integer `quantity_on_hand` — a consumption-rounding policy with a residual somewhere — and nothing in 021 makes or implies that decision. `lib/recipeQuantity.ts` validates the typed text in FULL and never by numeric prefix, the WP-A importer rule: `"150g"` and `"2abc"` are refused, not read as 150 and 2.

**A published recipe's physical quantities are its OWN snapshot.** A component names a unit — "1 box" — and what a box IS lives in `product_uoms.factor_num/factor_den` on the ingredient. That row is MUTABLE: `catalog.rs::save_product_tx` runs `UPDATE product_uoms SET factor_num = ?, factor_den = ?` on a product's selling unit whenever the owner edits the product. So a shop changing "1 box = 12 pcs" to "1 box = 24 pcs" would otherwise silently double the physical quantity of every published recipe that said "1 box", and double its cost, with no edit to the recipe and no record that anything happened. `product_uom_id_snapshot`, `factor_num_snapshot` and `factor_den_snapshot` are therefore NOT NULL, resolved from the database at save time and never taken from the client, frozen once the parent leaves `draft`, and keyed to the row they came from with `ON DELETE RESTRICT`. **The coherence rules hold on UPDATE as well as INSERT** (`trg_recipe_components_coherence_{ins,upd}`): the first cut applied them on INSERT only, reasoning that a draft line is rewritten wholesale rather than patched — which described the SAVE COMMAND, not the database. `UPDATE recipe_components SET factor_num_snapshot = 1000000` was accepted on a draft, and activation published a cost a million times too high, because the snapshot is exactly what it trusts. A trigger that holds only for the one writer that does not need it is not a guard. `activate_recipe` additionally PROVES each draft component's snapshot against the ingredient's current unit row rather than trusting it, which also catches the case no trigger can: a draft whose ingredient's unit has since been redefined is refused by name and the operator is told to re-save it, so a re-snapshot happens deliberately and under their eye instead of silently. A PUBLISHED line is never reached by any of that — the frozen-parent rule refuses the UPDATE first — so its conversion is never re-validated and never rewritten. An edited factor changes what the NEXT draft snapshots and nothing already published. A blocking trigger on `product_uoms` was considered and rejected because it deadlocks — the owner could not change a factor until they re-versioned the recipe, and re-versioning would re-snapshot the factor they were trying to change. The snapshot already makes the recipe immune, so the only remaining problem is that the recipe and the catalogue can DISAGREE, and `recipesRepo` surfaces that drift per line rather than hiding it: a difference the owner can see is a decision they can make. It reports THREE states, not a boolean — `current`, `drifted`, `unavailable` — because a unit row that has been deactivated or deleted leaves the catalogue columns NULL, and a boolean read that as healthy when it is the worse of the two problems: a drifted unit can be re-saved against, a missing one cannot. Equivalence is decided by cross-multiplying in integers (`sameConversion`), so `1000/1` and `2000/2` are one conversion; comparing the quotients as floats would make the warning appear and disappear with the arithmetic rather than with the data.

**A recipe's IDENTITY is fixed at creation, not at publication.** `id`, `store_id`, `product_id` and `version` can never change in any state (`trg_recipes_identity_immutable`), and `recipes.store_id` must equal its own product's store on INSERT and UPDATE. The first cut protected the header only once `status <> 'draft'`, which left a draft re-pointable by direct SQL at another product or another STORE — and `activate_recipe` would then publish it, read a cost pool from a branch it has no claim on, and retire that branch's incumbent. A draft is a document in progress, not a scratch row: what it is FOR is decided when it is created and only its contents are drafted. `activate_recipe` and `retire_recipe` also read the row by id ALONE and then PROVE ownership against the product's store, rather than filtering by the caller's store and reading a miss as "not found" — the two differ in exactly the case that matters — and every incumbent query and retirement UPDATE is scoped by store AND product AND the status it expects, so a corrupted header can only ever retire a recipe of the store and product that were proved.

**The lifecycle is three states and the timestamps ARE the state.** `draft` has neither; `active` has `activated_at`; `retired` has both — so **retiring preserves activation history**, recording when a version stopped being authoritative without erasing when it started, and a version that was never activated cannot be retired at all because the CHECK forbids expressing it. Editing an active recipe creates `version + 1` as a draft and never touches the published one; activating retires the incumbent in the SAME transaction, with `ux_recipes_one_active` making any other outcome impossible (the `ux_shifts_one_open_per_store` mechanism), and `ux_recipes_one_draft` stops "edit the recipe" accumulating rival drafts. `trg_recipes_lifecycle` refuses every illegal transition by name, a CHECK forbids `retired_at` preceding `activated_at` (both hold the project's canonical fixed-width UTC timestamp, so lexicographic order is chronological order), a published header's yield, **notes and creation time** are part of what was published and cannot be edited, and a published version's lines take no INSERT, UPDATE or DELETE, while a component never changes parent at all — migration 011's and 012's lessons, learned there on credit-memo lines.

**One level of composition, so a cycle is INEXPRESSIBLE rather than detectable.** An ingredient may not itself be recipe-costed and may not own a recipe in any state, and a product already used as an ingredient may not acquire one — both directions, because otherwise the same two-level chain is reachable by doing it in the other order. There is therefore no recursive cost walk to write and no depth limit to choose. Sub-recipes are a later work package and will bring their own cycle detection with them.

**An ingredient's rate is WP-B1 reused, and there is no recipe-level override.** A component's cost comes from the component's own `costing_method`: a typed `standard` figure, or `avg_cost_excl_vat_microcents`, or — when that pair is zero — **the P1-A predicate exactly as it stands**, `posting.rs::has_purchase_valuation_basis`. A documented `purchase` or `opening` movement makes the zero an ANSWER (a free case, a sample, an opening count valued at nothing); its absence makes it the absence of one, and the ingredient is reported as having NO cost. **Missing evidence is never treated as a legitimate zero**, and a cost that cannot be computed is reported as ABSENT rather than as 0, because returning zero is how a catalogue of 100% margins stops looking like a problem. A typed override on the component was rejected: for a stocked ingredient it would be a rate that disagrees with the `inventory_movements` ledger those goods left through, which is the defect WP-B1 refused when it restricted Manual Cost to non-stock items, one level deeper and harder to see. The supported way to state a cost for a stocked ingredient is to receive it on a document; a non-stock one can carry a Manual Cost today.

**A draft may be incomplete; a published recipe may not.** `save_recipe_draft` stores an incomplete recipe and NAMES the ingredients with no cost, so the owner can build it and see what is missing. `activate_recipe` refuses it, by ingredient name, and that refusal is what will make it safe for WP-B2-B to refuse a sale whose recipe cannot be costed: a cost basis is MONOTONE, since `inventory_movements` is append-only and an ingredient that has a purchase or opening row keeps it for ever, so an activated recipe cannot become uncostable through anything a shop does to its purchase history. Activation re-reads every rate and every eligibility against today's database — a draft saved last month against an ingredient since deactivated must not publish — while the physical quantities stay the draft's own snapshot.

**Recipe arithmetic accumulates six digits finer than a microcent, and says so.** `src-tauri/src/recipe_cost.rs` is the authority and `src/lib/recipeCost.ts` mirrors it for the editor's live preview, pinned by shared fixtures both suites assert (`recipe_cost::FIXTURES`). Each component collapses to ONE integer division — `round(rate x q_num x f_num x (10000 + waste) x ACC / (q_den x f_den x 10000))` with `ACC = 1,000,000` — and the batch is divided by the yield once at the end. There are TWO rounding points, not one, and the module says so rather than claiming otherwise: the per-component error is bounded by 64 / 2,000,000 of a microcent against a final unit of 1, and in the common case (`waste_bps = 0`, both denominators 1) the division is exact and nothing rounds at all, which is asserted. The mirror uses `bigint`, not `number`, because the worst-case numerator reaches 2 x 10^35 and a double carries 53 bits — a `number` implementation would lose precision quietly, which is the one failure mode this codebase will not accept in money. The admissible envelope is stated as a table with its overflow proof (rate <= 10^13, quantity and conversion parts <= 10^6, waste < 10^4, 64 components, yield <= 10^6, worst case 2 x 10^35 against `i128::MAX` of 1.7 x 10^38), migration 021 carries the same bounds as CHECK constraints, every multiply is `checked_mul`, and anything outside is REFUSED by field and limit. A silently clamped cost is a wrong number that looks like a right one.

**A RECIPE NOW COSTS A SALE, and that is the whole of WP-B2-B (migration 022).** B2-A could author, version and publish a recipe and no product could select it. 022 is the other half: it REPLACES migration 020's `trg_products_costing_coherence_{ins,upd}` pair — DROP then CREATE, the way 017 replaced 016's weak shift guard, because a v21 database already carries the refusing version and `IF NOT EXISTS` would keep it — so `costing_method = 'recipe'` is admitted **under two conditions** rather than refused outright: a NON-STOCK item, and a PUBLISHED recipe to cost it from. `post_sale` gains one branch, `recipe_sale_cost.rs::cost_sale_line_from_active_recipe`, which is checked FIRST among the product-level methods and fills `sale_items.cogs_source = 'recipe'` plus the new `recipe_id` / `recipe_version` columns. Nothing else about the money changes: the rate is a microcent figure per base unit like every other, and it becomes money exactly once, at `extended_cost_cents`.

**Recipe COGS is an ESTIMATED ingredient-based food cost, and B2-B says so everywhere it appears.** No ingredient `inventory_movements` row is written, no ingredient's `quantity_on_hand` or `avg_cost_*` moves, and there is still no `consumes_stock` column — a column with no reader is a promise the engine has not made. So the figure answers "what did this plate's ingredients cost at the rates on file", and it is NOT evidence that any ingredient was depleted. Consumption is WP-B3, which will have to decide what half a bun does to an integer `quantity_on_hand`, and nothing in 022 makes or implies that decision. The UI, the locales and the Sales History breakdown all state the limit rather than leaving a reader to infer it; reporting already placed `recipe` in the ESTIMATED row beside `standard` and opposite DOCUMENTED, which WP-B1 anticipated and B2-B did not have to change.

**Restricted to non-stock items, for WP-B1's financial argument unchanged.** For a stocked product the COGS rate is not merely a reporting figure: it is written onto the sale's `inventory_movements` row, and that ledger is what makes stock auditable, because `quantity_on_hand` and `avg_cost_*` are maintained together so the quantity and the value of the shelf agree. A recipe-derived rate there would say the goods left at one price while the pool they left from says another, and the movement table is append-only, so nothing could ever unwind it. A service line writes no movement, decrements no stock and touches no pool — no second figure to contradict. A restaurant's prepared items ARE the service case.

**Two different ages, on purpose.** The PHYSICAL figures — which ingredients, how much of each, at what conversion, with what waste — are the published version's own frozen snapshot, read from `recipe_components` and used exactly as stored; the CURRENT `product_uoms` factor is never consulted at post time, so a shop that redefines "1 box" changes what the next DRAFT snapshots and nothing a published version says. The RATES are resolved against today's database. That is the same split B2-A established and the one every other cost input here already has: repricing an ingredient changes what the NEXT sale is costed at and restates nothing already posted, because `sale_items` is sealed by migration 012. Publishing version 2 does not recalculate a sale costed from version 1, and changing the product's costing method afterwards restates nothing either.

**An ingredient with no cost basis REFUSES the sale; a documented zero posts.** The rate comes from the ingredient's own `costing_method` — WP-B1 reused, including the P1-A predicate `has_purchase_valuation_basis` — so a `purchase` or `opening` movement makes a zero an ANSWER (a free case, a sample, an opening count valued at nothing) and its absence makes it the absence of one. Missing evidence is never treated as a legitimate zero: the till stops and NAMES the ingredient. `activate_recipe` already refuses to publish a recipe whose ingredients cannot all be costed and a cost basis is monotone, so the only route to this refusal is somebody RECONFIGURING an ingredient after publication. An INACTIVE ingredient is deliberately not a refusal: deactivating a product destroys no purchase history and leaves the rate exactly as documented, so refusing would stop a shift over a catalogue tidy-up. A refusal returns `Err` and the whole transaction rolls back, so the receipt number is un-consumed with everything else and nothing partial is left behind.

**A posted recipe cost carries its own EVIDENCE, and a sale cannot post without it.** `sale_item_recipe_costs` (one row per ingredient per sale line) freezes the component's name, unit, exact quantity fraction, conversion snapshot, waste, the rate it was costed at, that rate's source and its contribution to one batch. Rows rather than a JSON blob because that is this project's convention for document children — sealed by triggers, scoped by store, joined by reporting — and because a blob is a schema nothing validates. It is sealed HARDER than `sale_items`: no UPDATE and no DELETE in any state, and no INSERT once the parent sale has posted. Without the breakdown frozen beside the receipt, "why did this burger cost $1.74 in March?" has no answer today's database can give, and a gross-profit figure nobody can explain is one nobody should trust. `trg_sales_recipe_evidence_complete` fires on the promotion to `posted`, so the invariant is a property of the ENGINE and not of one command — which matters because `post_sale` is not the only writer a database can have.

**"Complete" means the SET, not the presence of a row.** The first cut of that guard asked only "does at least one evidence row exist for this line?", and a four-ingredient burger with one hand-written row therefore posted: the receipt carried an explanation of a quarter of its own cost, sealed for ever, with nothing in the database saying the other three were missing. The guard now compares the evidence set against the cited recipe VERSION's component set in both directions and by count, re-proves every relationship the insert guard proves, and requires every frozen physical figure on every row — quantity fraction, unit, conversion snapshot, waste, store — to equal the published component's own.

**What the database can and cannot prove about the ARITHMETIC, stated rather than implied.** `recipe_cost.rs` is the authority: it accumulates in `i128` at a scale of ACC = 1,000,000 finer than a microcent and its worst-case numerator is 2 x 10^35, while SQLite integer arithmetic is 64-bit and SILENTLY PROMOTES TO FLOAT on overflow — so that expression cannot be reproduced in SQL at all. `contribution_microcents` is also the accumulator figure already ROUNDED to a microcent, and the accumulator value is not stored, so the batch total cannot be recovered exactly in SQL even in principle. Migration 022 therefore claims two different things and no more. STRUCTURE AND PHYSICS are proven exactly, by integer and text equality, with no arithmetic that can overflow. ARITHMETIC is reconciled inside an envelope with a written overflow proof — every part is first held to migration 021's own bounds (the CHECKs say the same thing, but a BEFORE INSERT trigger fires before a CHECK is evaluated), then two magnitude gates keep both products at or below 4 x 10^18 against an i64 limit of 9.22 x 10^18 — and anything OUTSIDE the envelope is REFUSED by name rather than skipped, which is the only fail-closed reading of "the database cannot check this one". Two relations are checked: each row's contribution is within ONE MICROCENT of `rate x qn x fn x (10000+waste) / (qd x fd x 10000)`, and the line's own rate satisfies `|U x Y - SUM(C)| <= Y + n` against the published batch yield. Both are TOLERANCES, sized by the two rounding points `recipe_cost.rs` documents, and they are named as tolerances. Both are TOLERANCES on a RATE, and they are named as tolerances.

**The MONEY, though, is reconciled exactly, and that division of labour is the answer to "a tolerance is not a proof".** Leaving the three CENT columns unchecked was the gap: a writer could file 174 cents of faithful ingredient evidence against a line booking 1 cent of cost, and every gross-profit figure the application prints reads the cents, not the microcents. So `sale_items.unit_cogs_excl_vat_cents`, `sale_items.line_cogs_excl_vat_cents` and `sales.cogs_total_cents` are each re-derived in SQL by `cost.rs`'s own rule — `(U + 500000) / 1000000`, `(U x Q + 500000) / 1000000` and `SUM(line_cogs_excl_vat_cents)` — and a disagreement of one cent refuses the promotion. Three things there are easy to get wrong and are therefore written out. The line cost is NOT the unit cost in cents times the quantity: `post_sale` multiplies the PRECISE microcent rate by the quantity and rounds ONCE, so three portions at 14,756,250 microcents are 44 cents where 15 x 3 would be 45 — the whole of GP-A03, at the cent boundary. Rounding is half AWAY FROM ZERO, which for these non-negative columns is `(n + 500000) / 1000000` under truncating integer division, exactly what SQLite's `/` does on two positive integers; `ROUND()` appears nowhere, because it is floating-point and a float is not a rounding rule. And `sale_items.quantity` is `INTEGER NOT NULL CHECK (quantity > 0)` from migration 001, so there is no fractional sale quantity to accommodate — a RECIPE quantity is a fraction and a SALE quantity is not, which is migration 021's own asymmetry. The header is reconciled over EVERY line of the sale, so a mixed recipe/manual/purchase-average receipt is checked as a whole; it is scoped to sales holding at least one recipe-costed line, because widening it to every document would be a new rule for documents this work package has no finding about.

**The tolerance cannot hide a cent, and the aggregates cannot overflow, because the component count is bounded in the engine.** `recipe_cost.rs` has always set `MAX_COMPONENTS = 64` and proved its envelope against that number, and migration 021 carried no matching rule — so a direct-SQL recipe of ten thousand ingredients could reach the SQL aggregates, where `Y + n` becomes an unbounded licence to misstate the rate and `SUM(contribution_microcents)` drifts towards the point at which SQLite stops being exact. `trg_recipe_components_max_count` refuses the 65th ingredient at the moment it is written, and the promotion refuses a sale from an oversized recipe BEFORE it aggregates anything, so a recipe that is already oversized in some database keeps its rows (nothing is deleted, nothing restated) and simply cannot cost a sale. With `n <= 64` and `Y <= 10^6` the microcent slack is at most `1 + 64/Y` microcents per selling unit — under a hundredth of a cent — against cent columns that are exact.

**Three facts about SQLite decide the shape of all of it, and they were measured rather than remembered.** `*` and `+` on two INTEGERs SILENTLY PROMOTE TO REAL on overflow and raise nothing, so a comparison against an overflowed product is worthless and every multiplication must be gated first. `SUM()` over INTEGERs RAISES `integer overflow`, which is fail-closed and is used as a backstop, never as the bound. And INTEGER AFFINITY IS NOT A TYPE: a column declared INTEGER holds `1.5` as a REAL and `'abc'` as TEXT, only a lossless numeric is converted, and `typeof(2.0)` is `'real'` — so every figure the database multiplies, divides or sums is first held to its integer STORAGE CLASS, then its RANGE, then a MAGNITUDE GATE, in three SEPARATE statements in that order. They cannot be folded into one `WHERE ... OR ...`: SQLite promises no evaluation order inside a boolean expression, and an unproven short-circuit is exactly how an overflowed product reaches a comparison. Affinity is applied before a BEFORE-trigger sees `NEW.x`, which is what makes `typeof(NEW.x)` a usable guard at all.

**A sale has TWO markers of one fact, and until WP-B2-B's last correction they could disagree.** `sales.status` and `sales.posted_at` both say whether a sale is real, and migration 001 tied them together only in a comment — "posted_at IS NOT NULL => row is immutable. Set when status moves to 'posted'". Which one is authoritative depended on who was asking, and that was the defect. The APPLICATION reads `status = 'posted'`: **37 query sites** across Sales History, the shift summary, the drawer reconciliation and every profit report, and **not one of them reads `posted_at`**. The ENGINE read `posted_at`: 001's immutability trigger, 012's child guards, and 022's own finalization. So `UPDATE sales SET status = 'posted'` made a sale financially real to every reader while changing no column any guard watched — no evidence check, no cent reconciliation, no component bound — and left the row mutable afterwards, along with its lines, whose guards key on the PARENT's `posted_at`. A sale could be counted in a shift report and still be edited.

**The legal state machine is three states and two transitions.** `INSERT` produces `(draft, posted_at NULL)`; posting moves it to `(posted, posted_at = now)` in ONE statement; 001's carve-out moves a posted sale to `(voided, posted_at unchanged)`. Nothing else. `post_sale` is the only writer of this table in the whole application — `post_credit_memo` writes `sales_credit_memos`, a separate family, and the frontend repos are read-only — and it has always issued exactly those two statements, in every committed version (checked at 5bc99cd, 2604d8c and f5939b5), so posting was already atomic and needed no change to satisfy the contract. The admissible pairs follow: `draft` implies no timestamp, `posted` implies one, and `'voided'` is deliberately unconstrained in both directions, because a voided sale keeps the `posted_at` it was posted with while a future "discard this draft" flow would legitimately void a row that never posted — and neither shape is financially recognised, since every read model filters `'posted'`.

**A sale is BORN A DRAFT, and that is why the INSERT rule is a shape rather than a validation.** `trg_sales_born_a_draft` refuses any INSERT that is not `draft` with no timestamp. Supplying both `status = 'posted'` AND a timestamp is not a way round it; it is the shape being refused — because validating a posted INSERT is impossible in principle, not merely awkward: a sale's lines and its evidence reference the sale, so at the moment the header arrives there is nothing to check, and afterwards 012's `trg_sale_items_no_insert_after_post` refuses to let the lines arrive at all. An INSERT that arrived already posted could therefore only ever be an empty receipt whose header columns claim whatever revenue its author typed. `trg_sales_posting_state_coherent` then forbids the incoherent pairs on UPDATE and every route backwards: clearing `posted_at`, rewriting it, returning `status` to `'draft'`, or moving a posted sale's status anywhere but `'voided'`.

**Finalization fires on the TRANSITION, not on a column.** `trg_sales_recipe_evidence_complete` is no longer `BEFORE UPDATE OF posted_at`: its `WHEN` matches either marker moving into the posted state. That is deliberate rather than belt-and-braces — it makes the money validation correct **independently** of the state trigger, so nothing depends on the order in which SQLite fires two BEFORE UPDATE triggers on one table. One trigger forbids the incoherent states, the other validates the money on the way in, both must pass, and either alone closes the bypass. A void re-fires neither, because `NEW.status` is `'voided'` and `posted_at` does not move: a posted sale is validated once, when it posts.

**Legacy data is not rewritten, and the residual is stated.** Both rules are BEFORE triggers, so they bind writes from the moment 022 applies and touch no existing row. A database that somehow already holds `status = 'posted'` with `posted_at IS NULL` keeps it — and can be REPAIRED, because supplying the missing timestamp is an UPDATE that satisfies the state rules and runs the full finalization validation on the way through. No shipped `post_sale` can have produced such a row. What remains true of one if it exists: its own header is now guarded, but its LINES are not, because 012's child guards key on the parent's `posted_at` and this migration does not widen them.

**Only a PUBLISHED version may cost a NEW sale.** Proving the product, the store and the version number establishes WHICH recipe is meant; it does not establish that the recipe is the authoritative one, and for two cuts migration 022 stopped there. A DRAFT is the dangerous case, because migration 021 deliberately lets a draft's components be edited: anything the engine proves about evidence written against one can be falsified afterwards, so the proof is worth nothing. A RETIRED version is the quieter case — it was superseded precisely because it no longer states what the kitchen makes. The rule is therefore enforced at three points, and all three are needed: the line INSERT, the line UPDATE (so a draft line cannot be re-pointed at an unpublished version), and the PROMOTION, because a draft sale persists between statements and the state that matters is the one at FINALIZATION. Nothing honest is caught by the third: `post_sale` writes the line, the evidence and the promotion in ONE transaction and SQLite serialises writers, so a recipe cannot change status in between. Reads are untouched — a trigger does not fire on a `SELECT` — so a sale legitimately posted from v1 stays readable, and immutable, for ever after v1 retires; and version replacement is untouched, because `activate_recipe` promotes v2 and retires v1 in one transaction and `post_sale` costs from whichever is active when it runs.

**The three columns are one fact, and they may not disagree.** `trg_sale_items_recipe_coherence` refuses a `'recipe'` line with no identity (it could never be explained), an identity under any other `cogs_source` (it would claim a provenance the rate does not have), and an identity that is not a recipe of the line's own store AND own product AND that version. It fires only when `recipe_id` or `cogs_source = 'recipe'` is present, or when evidence already hangs beneath the row, so every pre-v22 line — both columns NULL, no evidence — is untouched: history is not restated.

**It holds on UPDATE as well as INSERT** (`trg_sale_items_recipe_coherence_{,_upd}`). The first cut guarded INSERT only and reasoned that a posted sale's lines are immutable anyway — which describes a POSTED sale. Migration 012's guard fires only when the OLD or NEW parent is posted, and every posting command builds a DRAFT and promotes it last, so between those two statements a sale's lines are ordinary updatable rows. That window admitted three edits: a line with evidence beneath it REPARENTED from draft sale A to draft sale B, leaving the explanation filed against A and the charge against B with every foreign key still satisfied; `UPDATE sale_items SET recipe_id = <another store's recipe>` on a draft, which the INSERT guard would have refused and no guard saw; and an edit to `unit_cogs_excl_vat_microcents` after the evidence was written, so the posted rate and the explanation beneath it describe different costs — permanently, because the evidence takes no UPDATE and no DELETE in any state. So ONCE EVIDENCE IS ATTACHED THE LINE'S IDENTITY AND COST ARE FROZEN, which is a stronger rule than "a posted line is immutable" and the right one: the evidence explains exactly those figures, and the only writer that attaches it writes both in one transaction and never revisits either. A recipe-involved line is also never moved to another sale at all, evidence or not. And a recipe-involved line's store must be its SALE's store — nothing in the schema said so before, and every cross-store proof compares the evidence against the LINE, so a store-B line under a store-A header carried store-B evidence coherently onto a store-A receipt. The general `sale_items` case is deliberately not widened here: every row ever written would have to be re-proved against it. `recipe_version` is denormalised beside the FK on purpose; `recipes.version` is immutable, so the join would give the same answer, but a reader of a five-year-old receipt should not need one.

**Configuration is refused where the mistake is made, not at the till.** A product set to `recipe` with no published recipe cannot be sold at all, so `save_product` refuses it with a sentence naming the screen to use, and 022's trigger pair holds the same rule against every other writer. B2-A's `retire_recipe` already refuses to retire the active version while the product is recipe-costed, and `trg_recipes_no_retire_while_product_depends` now holds that rule against direct SQL as well — because two commands refusing each other's mistake is not an engine invariant, and one `UPDATE recipes SET status='retired'` went straight between them, leaving a product configured for a cost it could no longer obtain and a refusal that then arrived at the till. The guard is NOT a flat "never": `activate_recipe` publishes version N+1 by retiring the incumbent FIRST, inside one transaction, so that `ux_recipes_one_active` is never momentarily violated, and a flat refusal would make a recipe-costed item's recipe uneditable for ever — the deadlock reachable from the one workflow the feature exists for. So retirement is refused while the product is recipe-costed UNLESS a DRAFT version of that product exists, which is the only shape an atomic replacement takes (`ux_recipes_one_draft` makes it single-valued and `activate_recipe` promotes exactly it). The residual, stated rather than glossed: a direct-SQL writer can insert a draft, retire the incumbent and never activate. That is not a misstated figure — `post_sale` refuses such a line by name before a receipt number is consumed — and closing it would need a deferred constraint, which SQLite does not have. The Products form OFFERS the option unconditionally and refuses it conditionally, stating both conditions inline beneath the select: hiding a setting from an owner who does not qualify leaves them no way to find out why. A previously typed Manual Cost is carried through rather than wiped — it is inert under `recipe`, and destroying it would lose the owner's figure the moment they tried the other setting.

**Three figures, three names, on every screen that shows a recipe cost.** A recipe that makes twenty pots has ingredient quantities for the BATCH, a batch YIELD, and a cost per SELLING UNIT, and the posted breakdown printed only the first — so a reader took $2.95 of ingredients as the cost of one $2.00 pot and read a loss where the real cost is $0.1476. The panel now states "one batch makes N", the batch cost, and the line's own per-selling-unit rate, says in a line of its own that the quantities below are for one batch and that the line was costed at the batch divided by N, and labels its columns accordingly. The frozen yield comes from the published `recipes` row by join, which is safe because a published header's yield can never change (021), so the join returns the figure the sale was costed against and not today's. Nothing stored changes and no historical breakdown is restated.

**The Products list prices a recipe-costed item from its RECIPE.** `costConfigurationStatus` and `effectiveUnitCostMicrocents` had no `recipe` branch, so a correctly configured item fell through to a non-stock product's zero average and the catalogue printed "—" over the word "None" about the one item whose cost the owner had built a recipe for. Both now take the product's active-recipe cost, and the row says `recipe`, `recipe_missing` (no published version — the item cannot be sold at all) or `recipe_uncosted` (a version is published and an ingredient has since lost its cost basis, so the till would refuse it) — three states with three different remedies rather than one silent gap. The figure comes from `recipesRepo.summaries`, which costs every active recipe of the store in two queries through `lib/recipeCost.ts`, and is ABSENT rather than zero whenever it cannot be worked out. `costSourceShortKey` derives the label from the STATUS rather than from `costing_method`, so a method with no usable figure behind it cannot advertise itself as the source of one. An inert Manual Cost left on the row is never printed while the method says `recipe`.

**The coverage panel's ESTIMATED row covers both estimates.** `reportMath.ts` has counted `recipe` beside `standard` since WP-B1, and only the wording lagged: it said "manual costs" and described what the owner typed. Both locales now name a manual cost OR a recipe cost worked out from its ingredients' rates, and state in the same breath that a recipe cost does not consume ingredients out of stock and is reconciled against no stock figure — so a difference between it and what the kitchen actually used will not appear anywhere in the report.

**A refunded prepared item reverses revenue and NOT the food cost**, and this needed no new code. Whether a line may be restocked is decided by whether the SALE produced an inventory movement, and a non-stock line produced none — so a recipe-costed return restocks nothing, reverses no cost and blends nothing into any pool. The margin on food already made and discarded is lost, which is the truth about it, and no ingredient movement is invented in its place.

**The discount permission binds the ECONOMIC discount, not the declared one (GZ-B-P1, closed in V1).** `post_sale` persists the unit prices and line totals the request carries, so authorizing only `discount_cents` let a hand-built request sell a $10.00 item for $0.01 with no discount declared. `posting::sale_price_shortfall_cents` now reads, inside the posting transaction and after the replay resolution, the price the CATALOGUE gives each line's product in its resolved unit (`product_uoms.sale_price_*`, else base price × factor rounded half-up — `lib/uom.ts::resolvePriceForUom` exactly), and counts per line the largest of the excl unit-price shortfall, the incl unit-price shortfall, and catalogue incl × quantity minus the posted (post-discount) incl line total. The economic discount is `max(discount_cents, Σ lines)` — the line term already includes each line's discount allocation, so the two are never added. Over `DISCOUNT_WITHOUT_APPROVAL_CENTS` it needs `PostSaleLargeDiscount`. A price below the catalogue is AUTHORIZED rather than refused, because a cart line holds the product as it was when rung and a manager may reprice mid-shift; the refusal tells the cashier to re-add the item. The exclusive line TOTAL is deliberately not compared: `save_product` does not hold a product's excl/incl pair coherent, and the register derives the post-discount excl subtotal from the incl figure. A boundary preflight (`economic_discount_preflight`, new identities only) asks the AUDITABLE `authorize` so a hidden-price refusal leaves a `permission_denied` row; the in-transaction check remains the authority. (The VAT-split residual this paragraph used to state is closed by GZ-VAT-1, below.)

**The revenue/VAT split of a NEW sale line is the database's (GZ-VAT-1).** `validate_line_financials` proves only that a line's parts add up, and the rate used to be the caller's — `vat_rate_id_snapshot` / `vat_rate_bps_snapshot` were stored as sent — so a request could post a taxable item as exempt, or move revenue into VAT, with the customer's total unchanged. `posting::validate_sale_vat_authority` now runs inside `post_sale_tx`, AFTER the replay resolution (a sale that already posted replays on the terms it posted under; no historical row is re-judged) and before any number is consumed: the line must name the product's own `vat_rate_id` and carry that row's `rate_bps` (zero-rated and exempt are both 0 bps and are still distinct rows), and the exclusive subtotal must be `strip_vat(line_total_incl, bps)` with VAT the remainder. That is the register's one posting rule — `lib/discount.ts::postDiscountLineTotals`, which every line goes through, discounted or not — so no second VAT formula exists; both sides are held to the same exact rounding specification by `tests/vat_authority.rs` and `tests/unit/discount.test.ts`. The per-unit-times-quantity figures in `lib/saleMath.ts` are pre-discount display only and never reach a posted line. A disagreement is REFUSED, never rewritten; a product whose rate changed while the cart was open gets the same "remove the item and add it again" remedy as a repriced one. The size of the inclusive total itself is the economic-discount rule's job (GZ-B-P1). Not decided here, deliberately: `vat_rates.effective_from/effective_to` are not consulted (nothing in the application does today), so the rate is the one the product row points at.

**A cashier reads through a different SQLite authorizer (Stage C, GZ-B3-R1).** `db_select` still takes SELECT text, so confidentiality cannot be a property of the text. `read_api::read_pool_for_state` resolves a tier on EVERY read via `authz::read_tier` — the stricter of the session's role and the role on the user's own row, so a demotion bites on the next query — and a tier without `ReadCostAndMargin` is served by a separate read-only pool whose connections carry `read_guard::cashier_authorizer`. It denies, on resolved `(table, column)` pairs so no spelling of a query avoids it: whole tables (purchasing, suppliers and their ledger, `inventory_movements`, recipes and `sale_item_recipe_costs`, the accounting tables, `sync_queue`, `app_settings`); ANY column whose name contains `cost`, `cogs` or `variance`, so a future cost column is denied before anyone thinks about it; and a closed shift's `expected_cash_*` and `closing_cash_*` — the count is denied too, because with it a variance is one subtraction from tender rows a cashier may read. Each pool proves its own policy on every new connection before it is handed out. The CASHIER-REACHABLE reads of `products`, `sales`, `sale_items` and `shifts` name their columns: `src/db/projection.ts` lists public and confidential columns and appends the latter only when the session can see them (`tests/integration/stageCProjection.test.ts` holds the lists to the real schema), because a `SELECT *` there would be refused whole and take the barcode scan, the receipt or the shift screen with it. Supervisory-only repos (credit memos, purchasing, suppliers, reports) still use `SELECT *`; they are not on a cashier's screens, and the authorizer — not the projection — is what refuses them to a cashier. Readable to a cashier, by design: the catalogue and prices, sales and tender (revenue, not cost), driver balances (the remittance screen needs them), exchange rates. As ever, this is in-application confidentiality: anyone who can run a program on the Windows account can read the file (T9).

**One instance per identity per Windows user (GZ-A1-R2).** `single_instance.rs` takes a named Win32 mutex `Global\GreazPOS.<identifier>.<token user SID>` in `lib::run` BEFORE the Tauri builder, which is where `tauri-plugin-sql` opens and migrates the database. A second copy shows a native "already open" notice and exits 0 without touching the file; any failure to create or open the mutex, or to read the token SID, fails closed. Keyed by the token SID, not `USERNAME`, because an environment variable is the launcher's to change while the database path is not. Released by the OS however the process ends, so there is no stale lock to clear after a crash.

**Snapshots at post time.** `sale_items`, `purchase_items` and `sales_credit_memo_lines` snapshot price, VAT, COGS, and UoM at the moment of posting. These values never change after posting. Since WP-A2 that includes `sale_items.kitchen_note`, which is a snapshot of an instruction rather than of a figure, since WP-B1 `sale_items.cogs_source`, which snapshots how the COGS rate beside it was arrived at, and since WP-B2-B `sale_items.recipe_id` / `recipe_version` plus the `sale_item_recipe_costs` rows beneath them, which snapshot the whole working.

**Posted rows are immutable.** Database triggers prevent UPDATE/DELETE on posted sales, purchases, credit memos and inventory movements. Corrections are made via reversal rows, never edits.

**All three document families are sealed the same way** since migration 012: a posted sale, purchase or credit memo takes no new child row, no child UPDATE or DELETE, and no child reparented into or out of it. The reparenting guards test `id IN (OLD.parent_id, NEW.parent_id)`, because `sale_id` / `purchase_id` / `credit_memo_id` are ordinary updatable columns and a one-sided check on the OLD parent lets a child be moved into a settled document from a draft. The INSERT guards key on the parent's `posted_at`, which is why **every posting command builds a draft and promotes it last** — `post_sale` wrote `status = 'posted'` in its first statement until WP-07, which would have made that guard reject every sale. `supplier_ledger` needed nothing: it has been unconditionally append-only since migration 006, and WP-05's sign discipline is a BEFORE INSERT trigger, so a legitimate signed `adjustment` or `opening_balance` is still an ordinary insert.

A posted CREDIT MEMO is sealed harder than a posted sale, and deliberately so. Migration 001 lets a posted sale become `'voided'` if a listed set of columns is unchanged; migration 011 allows no UPDATE at all, no DELETE, and no new line or refund leg. Two reasons. A posted memo has already moved stock, re-blended the cost pool and taken cash out of the drawer, and WP-06 ships no void command — so a bare status flip would hide the refund from every `status = 'posted'` read model while leaving all three effects in place, which is a hole that balances nowhere rather than a void. And a column list is a denylist worn as an allowlist: the copied one omitted the shift, the cashier, the locked rate and the reason, so the statement that voided a memo could also re-point it at another drawer. The `voided_*` columns stay RESERVED for a future workflow that relaxes the trigger and writes the compensating entries in the same migration. And a memo line or refund leg NEVER changes `credit_memo_id` — not even between two drafts, which WP-06 permitted. `trg_credit_memo_lines_no_over_return` proves that a line belongs to an item of the memo's OWN original sale and that the quantity is still available, and it checks on INSERT only; so a line created under a draft against the sale it belongs to could be moved under a draft against a different sale and promoted, crediting a receipt that never sold the goods. Production reparents nothing, so forbidding it outright costs nothing and is cheaper than re-running those proofs on UPDATE. INSERT is guarded too, because adding a child to a settled document edits no existing row and so slips past an update guard — and the guard keys on the parent's `posted_at`, which is NULL throughout the command's draft construction phase.

**Stock and cost are not product metadata.** `products.quantity_on_hand` and `products.avg_cost_*` (microcents and their cents mirrors) are writable ONLY by the posting commands and `post_adjustment`, each of which writes an `inventory_movements` row alongside — which is what keeps `SUM(quantity_delta)` reconciling to `quantity_on_hand`. `save_product` cannot write either: there is no field for them on its payload, so the authority is removed rather than merely unused. The generic product UPDATE used to write them, and the Products page computed `quantityOnHand = form.isService ? 0 : existing` — so ticking “service” on a product holding ten units destroyed ten units of stock with no movement to account for it. Turning a stocked product that still holds stock into a service is therefore **refused**, reporting the quantity, and a zeroing movement is not fabricated in its place: the command does not know why the stock is going away, and a movement under an invented reason is worse than a refusal. The operator writes it off through the inventory-adjustment flow, which records the movement under a reason, and then reclassifies.

**Weighted-average COGS.** `products.avg_cost_*_microcents` is recalculated on every purchase post using `(existing_qty * old_cost + new_qty * new_cost) / total_qty`, accumulated in i128 at full microcent precision and divided once. No component is rounded to cents on the way.

### Data Flow: POS Sale

1. Cashier scans barcode → `BarcodeManager` resolves `Product` + `ProductUom` via repos
2. `saleMath.ts` computes line totals, VAT, COGS per line
3. Payment collected as split tender (USD cash / LBP cash / card / bank transfer)
4. Frontend builds `PostSalePayload` and calls `tauri.invoke('post_sale', payload)`
5. `posting.rs:post_sale` runs a single SQLite transaction:
   - INSERT into `sales`, `sale_items`, `sale_payments`, `inventory_movements`
   - UPDATE `products.quantity_on_hand`
   - SET `sales.posted_at` (triggers immutability)
6. Frontend refreshes from repos; shows receipt

## What counts as desktop evidence

These four are different things, and a claim is worth what its weakest word is. The distinction exists because a walkthrough that says "verified at 125% scaling" when it resized a viewport has not tested what it says it tested.

| Term | What it means here |
|---|---|
| **Real WebView2 evidence** | The actual Tauri application running against a real SQLite file under a disposable identity, driven over CDP. Rows read back out of that database afterwards are the strongest evidence this project produces short of a human at the till. |
| **Real key events** | `Input.dispatchKeyEvent` into the WebView — genuine keyDown/char/keyUp as Chromium raises them for a keypress, so focus, shortcut handlers and controlled inputs all behave as they do in use. It is NOT the Windows input stack: nothing here proves a physical keyboard or a scanner's HID output. |
| **Simulated UI interaction** | A click or a value set from page script (`element.click()`, a React-dispatched `input` event). Fine for setting up a scenario, worthless as proof that a control is reachable or focusable. |
| **Emulated viewport** | `Emulation.setDeviceMetricsOverride` at, for example, 1093×614 with `deviceScaleFactor: 1.25`. That is the CSS viewport a 1366×768 panel presents at 125% Windows scaling, and it exercises the layout — but it is a browser-level override. |
| **Actual Windows 125% scaling** | The OS display setting, which changes device pixel ratio, font rendering, WebView2 chrome and the window's own frame. It is NOT covered by any automated run in this repository; every walkthrough so far has run at 100%. Where it matters, say UNVERIFIED. |

## Lebanese Retail Specifics

- Default VAT rate: 11% (stored in `vat_rates` with temporal effective dates)
- Dual currency: USD is the base currency; LBP is the local tender
- Exchange rate locked at sale time (`sales.exchange_rate_id`) — not retroactive
- Products have both `price_excl_vat` and `price_incl_vat` in USD cents
